# Podbay security

Podbay stores and shows other people's mail, inside the user's own Cloudflare account. Four outcomes are critical here ([`SECURITY.md`](../../../SECURITY.md)): reading a mailbox without a membership, sending as someone else, running script from a message, and leaking a credential.

This skill is the Podbay half of rule S18 ([engineering rules](../../../docs/engineering-rules.md)). It says **what** must hold: the trust boundaries, their invariants, the rules that guard them and the proof that exists today. The **method** (how to hunt, validate and report) is Cloudflare's [`security-audit`](../security-audit/SKILL.md) skill, vendored next to this one.

| Skill | Holds | Edited here |
|---|---|---|
| `.claude/skills/security-audit/` | The audit method, severity anchors, report schema and validators. MIT, from Cloudflare | **Never.** `pnpm static vendored` compares every file with `vendored.json` |
| `.claude/skills/podbay-security/` (this file) | Podbay's boundaries, invariants, cadence, release gate, records | Yes, in the same change that moves a boundary or adds a proof |

The rule in one paragraph: a change to a boundary ships a regression test. A full audit runs before v0.1, before every release that changes a boundary, and every quarter. A confirmed critical or high finding blocks the release. Records live in [`docs/security/`](../../../docs/security/README.md).

### B1. Inbound mail bytes

- **Crosses:** a raw message from anyone on the internet, through Email Routing into the `email` handler. Envelope, headers, body, attachments and file names are all written by the sender.
- **Invariant:** the envelope recipient picks the mailbox, never a header. Nothing from a message becomes a Durable Object name or an R2 key without passing `workers/lib/inbound.ts` or `workers/lib/filenames.ts`. Parsing happens in one place, with size and time bounds, and its output is validated before it is stored. Logs carry opaque ids, never a body, a subject or an address.
- **Code today:** `mailboxAddressFor` and `routeInbound` in `workers/lib/inbound.ts`; `storageFilename` in `workers/lib/filenames.ts`; `shared/log.ts`, the only module that writes logs. **Arrival** (ADR-0015; `receiveEmail` in `workers/arrival.ts`, `workers/durableObject/originals.ts`): the mailbox is picked by the envelope before a byte is read; a declared size outside 1 byte to 25 MiB is refused with `setReject`; a row in `arrivals` is written, then the bytes are stored exactly and without metadata under a key made from 16 random bytes (`newRawKey` in `workers/lib/original.ts`), which holds nothing of the message; a stream of another length than declared is a failure that removes what was written and makes the handler throw. That is the line: after it the handler neither throws nor rejects. The message is parsed inside the handler, once; one transaction writes the message's row with the key and the size read from the arrival's own row, its attachment rows (marked `uploading_since`) and removes the arrival; then the files' bytes are written. A message the parser refuses, or whose text is too large for a row, is filed with its original alone (`unparsed`), joins no conversation and wakes no assistant. An arrival older than fifteen minutes is taken up by the next one, three at a time, each by a call that counts the attempt: parsed on the first, filed as `interrupted` from the second, removed when its bytes are not there. **Authentication** (`platformStatement` in `workers/lib/original.ts`): the first `Authentication-Results` field is read from the message's headers, cut at the first comma outside a quoted string or a comment, and kept only when its identifier is exactly `mx.cloudflare.net`; it is stored and, until the live check of decision 19 is recorded, said to nobody (`AUTHENTICATION_SHOWN` in `shared/original.ts`).
- **Proof today:** `test/unit/inbound.test.ts`, `test/unit/filenames.test.ts`, and `test/workerd/inbound.test.ts` (the `To` header cannot pick a mailbox; a message without `To` is delivered; unknown and malformed recipients are rejected and nothing is stored). `test/unit/log.test.ts` (an address in a log field is masked); `pnpm static ratchets` counts `console.*` calls outside the log module. **Conversations:** `In-Reply-To` and `References` are the sender's claim. A message joins a conversation only when a message with one of those ids is in the mailbox and has the same subject (`workers/durableObject/threads.ts`; `test/workerd/inbound.test.ts`: joins, is refused with another subject, keeps answers to unknown mail together, survives 400 references). **Arrival** (`test/workerd/original.test.ts`): the object equals what was sent byte for byte, also when it is not text, and has no metadata; the key matches its shape for a message full of path characters; the arrival's row is there when the bytes are written and a file's row when its bytes are; a size outside the limits is rejected and the stream is not read; a shorter or longer stream, and a bucket that fails, leave no row and no object and the handler throws; a message nested deeper than the parser goes, and one larger than a row, arrive as `unparsed` with the envelope sender and their originals; a handler stopped before filing leaves a row the next arrival finishes, a second attempt is filed as `interrupted`, a row without bytes is removed; the same message twice is two messages. **Authentication** (`test/workerd/original-routes.test.ts`, `test/unit/original.test.ts`): a second field with the platform's identifier is not taken, a first field with another identifier keeps nothing even when the platform's follows, and a quoted string or comment that never closes keeps nothing.
- **Open:** the live check of decision 19 (a forged field sent to a real domain; until it is in the ledger nothing is said about authentication), and a development instance, where nothing checks authentication and a field the sender wrote is believed. The queue consumer as the only parser, the hostile-message corpus, the static check on the parser import, validation of parsed output, the test that feeds marked content through every handler and scans the log output, the CPU budget.

### B2. Mail HTML and attachments in the browser

- **Crosses:** a stranger's HTML, links, inline images, attachment bytes, file names and declared types, shown inside a signed-in session. This is the one place a stranger's bytes meet the reader's session.
- **Invariant:** one renderer. The body is sanitised, placed in a document with a strict content policy, and shown in a sandboxed frame without same-origin access. Remote content stays out until the reader allows it. No other code injects message HTML. An attachment is a download: `Content-Disposition: attachment`, `nosniff`, and a risky type needs an acknowledgement that the server enforces.
- **Code today:** `app/lib/mail-html.ts` and `app/components/EmailIframe.tsx`; `scripts/checks/html.ts`. **Content policies** (`shared/security-headers.ts`): the page's (`PAGE_CONTENT_POLICY`, on the assets through `public/_headers`) starts from `default-src 'none'` and names only the app's own origin, plus three entries the mail frame needs because a `srcdoc` frame inherits its embedder's policy: the hash of the frame's sizing script (`shared/mail-frame.ts`), `'unsafe-inline'` styles and `https:` images. The frame's own policy stays narrower and decides whether a remote image loads. Everything the Worker answers carries `API_CONTENT_POLICY` (`default-src 'none'`, `sandbox`) and `Cross-Origin-Resource-Policy: same-origin`. **Attachments** (`shared/attachment-risk.ts`, the routes in `workers/index.ts`): always `Content-Disposition: attachment` with `headerFilename`, `nosniff`, and a type from a short list of inert ones or `application/octet-stream` (`servedContentType`), never the sender's. `attachmentRisk` names the kinds that are dangerous by design, by last extension, by declared type and by invisible characters in the name; for those a GET answers 409 and the bytes leave only through `POST …/download` with `{ acknowledged: true }`, which the guard accepts from the app's own origin only, and always as opaque bytes. Images a message embeds are fetched by the app and put into the body as `data:` URLs (`app/lib/attachments.ts`, `app/lib/inline-images.ts`): plain image kinds only, never SVG, with a size cap; the frame loads nothing from Podbay either. **The original of a message** (ADR-0015; `workers/routes/original.ts`): it is every byte a stranger sent, so it is never a page. `GET …/emails/:id/original` answers JSON with the first 256 KiB as text (UTF-8, U+FFFD for what is not, NUL dropped), read from the bucket by a ranged read. The bytes leave only through `POST …/emails/:id/original/download` with `{ acknowledged: true }`, which the guard accepts from the app's own origin only: always `application/octet-stream`, `Content-Disposition: attachment` and a name Podbay made (`originalFileName` in `shared/original.ts`: the day and the start of the id, nothing of the subject or the sender). There is no GET for the bytes and no range. In the app (`app/components/email-panel/OriginalMessage.tsx`, `app/lib/original-text.ts`) the text goes into text nodes of one preformatted block that is laid out left to right whatever it holds; a control character, and a character that changes the direction of text or takes no room, is drawn as a mark with its code point; nothing becomes markup or a link. Before the download the app says, in its own dialog, that the file holds the whole message with every attachment and names the ones that can do harm.
- **Proof today:** `test/unit/mail-html.test.ts` (active content removed, remote content removed and counted, links, the content policy, the script nonce); `pnpm static html` with its tests in `test/unit/checks-more.test.ts` (no HTML injection in the UI, only the mail frame sets `srcdoc`); `test/unit/filenames.test.ts` (a file name cannot break out of the header). `test/unit/content-policy.test.ts`: the page's policy names no host, no wildcard, no `eval` and one script hash; the hash is the SHA-256 of the script and the script is exactly what the mail document contains; the frame needs nothing the page does not allow; the API's policy allows nothing. `test/unit/attachment-risk.test.ts`: the kinds, the last extension behind trailing dots, invisible characters, the type when the name hides it, the served types. `test/workerd/attachments.test.ts`: headers and bytes of safe files; every risky kind refused to a link (also with a query string) and handed over to the acknowledged POST as opaque bytes; the acknowledgement must be said, cannot come from another origin or from a request without one; a reader may download, a non-member is told nothing. `test/workerd/draft-files.test.ts`: a person's own uploaded file, and a file copied from another message, are served by the same routes and the same rules; a file is downloaded only under the message it belongs to; a risky file is copied into a draft only with the acknowledgement. **The original** (`test/workerd/original-routes.test.ts`): both answers carry the security headers and are never cached; the download is `application/octet-stream` with `nosniff`, its length and the name Podbay made, and equals what arrived byte for byte; without the acknowledgement, from another origin and without an origin it is refused; a GET on the download path gives no bytes, with or without the word in the address; a range is not honoured. `test/unit/original.test.ts`: the marks for control and direction characters, the file name for hostile ids and dates, a character the 256 KiB cut goes through.
**In a real browser** (`pnpm e2e`, the built app under its real headers in Chrome; `test/e2e/`): sixteen kinds of hostile message each run no script, contact no host (every connection the browser attempts goes to a recording proxy, so this covers the frame's own process), open nothing, leave nothing active in the frame and trip no policy there; the frame has an opaque origin and cannot read the app, cookies or storage; remote images load only after the reader asks and never over plain http; links open an ordinary window without an opener; the page's policy by itself blocks an inline script in a frame even with a valid nonce; attachments never render as pages. `original.spec.ts`: an original full of markup, a script, a link, an image address, a frame and direction marks is shown as characters, with no element of the message in the page and no link, runs nothing and requests nothing; the file is saved with the exact bytes and never opened; a link to the bytes gives none; a sent message offers neither. The frame's sandbox (`MAIL_FRAME_SANDBOX`) no longer allows moving the app's window. **Since 2026-11-17:** a resource address that is neither embedded data nor remote is removed in both modes (a relative address resolves against the app in a `srcdoc` frame), and quoted text at the end of a reply is folded into a `details` element inside the sanitiser's own pass, so the body is still parsed and written out exactly once (`test/unit/mail-html.test.ts`: both, and that what is inside the fold is cleaned). The one inline script also reports the height when a fold is opened; its hash in the page's policy changed with it, and `test/unit/content-policy.test.ts` holds the two together.
- **Open:** the browser tests run in Chrome only. Attachment risk goes by name and declared type; nothing inspects content or scans for malware. The page's policy has `'unsafe-inline'` styles and `https:` images because the frame inherits it; serving the frame from its own origin would let the page drop both. S12 applies as soon as the server fetches anything for a message.

### B3. Sign-in, sessions and step-up

- **Crosses:** credentials, session cookies, invitation and recovery links and step-up proofs, from any browser.
- **Invariant:** the design in [sign-in and access](../../../docs/auth-and-access.md). Invitation only. A new instance is closed until the guarded first-owner call. Sessions are server-side; cookies are host-only, `HttpOnly`, `Secure`, `SameSite=Lax`. Sensitive changes need fresh proof. Every authentication route is rate-limited and answers uniformly. Every state-changing request is checked against the app's own origin.
- **Code today:** Better Auth on D1 (`workers/auth/options.ts`, tables generated into `migrations/0001_auth.sql` and checked by `node scripts/auth-ddl.ts --check`). Password sign-in with a 12-character minimum; rate limits counted in the database. Accounts cannot be created over HTTP: the sign-up endpoint is refused, and accounts are made on the server by the guarded first-owner call (`POST /api/setup/owner`, needs the `SETUP_TOKEN` secret, works once, compared in constant time). An account without an instance role is not admitted. Every request that changes state must carry the app's own `Origin` (`sameOrigin` in `workers/auth/middleware.ts`). Cloudflare Access is an optional outer layer; a half-configured Access refuses to run. **Second step and passkeys** (Better Auth's two-factor plugin and `@better-auth/passkey`, tables in `migrations/0005_second_step.sql`): an authenticator app with recovery codes, enabled with the password and a first code, secrets and codes stored encrypted; `workers/auth/options.ts` refuses trusted devices (`trustDevice`), codes by mail or text message, and any method but the app. A passkey is bound to the request's hostname, needs user verification and a resident key, and is a complete sign-in. **Fresh proof (step-up)** has one definition (`workers/auth/fresh.ts`): the session signed in within `FRESH_SECONDS` (ten minutes), and signing in again replaces the session (`afterAuthEndpoint` deletes the one the browser held). Routes marked `fresh` in the route table are checked last in the guard, on the session read from the database; Better Auth's own endpoints that change how a person signs in are held to it in `beforeAuthEndpoint` (`FRESH_AUTH_PATHS`), and registering a passkey by the plugin itself with the same `freshAge`. Sign-in attempts are counted per `cf-connecting-ip`. **Recovery** (`workers/auth/recovery.ts`, `workers/routes/recovery.ts`, table in `migrations/0006_recoveries.sql`): a link is issued by someone else, never for oneself (`mayIssueRecovery`: an owner for anyone, an administrator for members only), with fresh proof; the operator issues one for an owner with `SETUP_TOKEN`, compared in constant time (`POST /api/setup/recovery`). A link is 256 random bits, stored as a digest, good for a day, and a new one replaces the old. Redeeming it is one D1 batch whose later statements run only if the first marked the link used: new password hash, every session deleted, authenticator app and passkeys deleted, program keys revoked, audit row. It signs nobody in and never shows an old credential.
- **Proof today:** `test/workerd/sessions.test.ts` (a person lists only their own sessions and only with fresh proof; ending one signs that browser out and no other; nobody ends a session that is not theirs; a password change needs the current password, ends every other session and retires the old password) and `account.spec.ts` in the browser. `test/workerd/access.test.ts`: a new instance answers 401 everywhere; the first-owner call is refused without the token, with a weak password and from another origin, and works once; HTTP sign-up is refused and creates no row; a wrong password and a forged cookie are refused; the session cookie is `HttpOnly`, `Secure`, `SameSite=Lax`; a cross-origin or origin-less mutation is refused. `test/workerd/second-step.test.ts`: the app is not in force before its first code; then a password alone gives no session; a wrong code, a code without the password step and a reused recovery code are refused; `trustDevice` is refused and the same browser is asked again; codes by mail are refused; guesses from one address are limited; the secret and the recovery codes are not readable in D1. A passkey registers only with a fresh session, signs in by itself (also for a person with an app), and is refused without user verification, for another origin or site id, when unknown, and when an answer is replayed. An eleven-minute-old session still reads and does ordinary work but is refused every sensitive change, with nothing changed and nothing revealed about a mailbox it may not manage; signing in again gives it back and leaves no older session. `test/unit/fresh.test.ts`: the window, the exact list of fresh routes, and that every Better Auth path named in the rules is an endpoint of the installed version. `test/workerd/recovery.test.ts`: who may issue for whom, never for oneself, never stale, never to a member or without a session; the token is not in D1 or the audit log; a person with a session, a passkey, an app and a key ends with the new password alone (old password refused, no code asked, passkey refused, key revoked, sessions gone); a link works once even for two requests at once; a short password does not use it up; unknown, replaced and expired links answer alike; the operator call needs the setup token and the app's origin, and serves owners only. `test/unit/recovery.test.ts`: the issue matrix.
- **Open:** no self-service reset (a recovery address outside Podbay and reset links by mail); the setup token is a standing owner-recovery credential unless the deployer removes it; Podbay's own public routes are not rate-limited; nobody is required to have a second step; a code can be reused within its 30 seconds; passkeys are tested with Chrome's virtual authenticator, not with a physical device; changing a password in the app; the app's own response headers (content policy, `frame-ancestors`, HSTS); session listing and revocation in the UI. Do not add a second way to create an account.

### B4. Per-mailbox authorisation

- **Crosses:** a mailbox, message or attachment id in a request, and the identity of the caller.
- **Invariant:** deny by default. One `authorize(actor, action, resource)` decides for every route, tool and connection, from one table. A non-member gets "not found". **Managing is not reading:** an owner or administrator without a membership cannot open a mailbox, and granting themselves one needs step-up, is audited and is visible to the mailbox's owners. An id from a request is resolved to an opaque id before it touches storage. Deleting a message or a mailbox removes its rows, its Durable Object data and its R2 objects.
- **Code today:** `authorize` in `workers/auth/authorize.ts` decides; `ROUTE_TABLE` in `workers/auth/route-table.ts` names the right of every API route; the guard in `workers/auth/middleware.ts` runs in front of all of `/api/*`, refuses a route that is not in the table, resolves the mailbox through the D1 index with the caller's membership, and names the Durable Object after the address stored in the index, never after the request. A non-member gets 404, whatever their instance role, with one exception that `authorize` names: `mailbox.members.read` and `mailbox.members.manage` are also allowed to an owner or administrator of the instance without a membership. The guard looks the mailbox up with the caller's membership or none (`mailboxFor`), sets the storage stub only when there is a membership, and lets `authorize` decide; so a manager reaches the member routes (`workers/routes/people.ts`) and the registry (`GET /api/v1/registry/mailboxes`: address, owners, member count) and nothing else. Every member change needs fresh proof and is recorded with whose membership, which role and in which capacity it was made (`membershipDetail`: `as: owner` or `as: manager`, `self:` for one's own); `memberHistory` reads that record back for the mailbox's owners, including a manager who added and removed themselves. A mailbox always keeps an owner. Deleting a mailbox purges its Durable Object and its attachments (`purge` in `workers/durableObject/index.ts`). The agent connection checks a session and the right to change mail in that mailbox (`mailboxDecision`). **Many conversations at once** (ADR-0014; `workers/routes/bulk.ts`, `workers/durableObject/deeds.ts` and `deed-steps.ts`): three routes, each `mailbox.write` in the route table. The request is parsed by one schema the app takes its types from (`shared/bulk.ts`): it names no target but Inbox, Archive, Spam and Trash and no change but a move, read, a star and labels, so nothing in it deletes for good or sends. A filter is the search route's own conditions (`buildSearchConditions`) and is only counted by the request that names it; acting is a second call that names the deed, whose id is opaque and is looked up in the database of the mailbox the guard picked. What a deed changed is kept for an hour as ids, places and marks, never content, and goes row by row with a message that is deleted for good. A filter deed is written to the audit log when it starts and when it is undone (`mailbox.bulk`, `mailbox.bulk_undone`) with who, which mailbox, which change and how many, never the filter. **The original of a message** (ADR-0015): both routes are `mailbox.read` in the route table. The message id only looks a row up in the database of the mailbox the guard picked (`originalOf` in `workers/durableObject/originals.ts`), and the key of the object comes from that row and from nowhere else: no code builds the key of an original. `raw_key` and `auth_results` never leave the mailbox object in an answer about a message (`shownMessage`), which says `has_original`, `raw_size` and `unparsed`. **Deletion** (rule S13): objects go before rows. One function deletes a message (`deleteMessage` in `workers/lib/messages.ts`: its files, its original, then its rows); emptying a place names a batch and its objects, deletes the objects, then the rows of that batch (`workers/durableObject/emptying.ts`); deleting a mailbox reads the keys of every file, every original and every arrival (`allKeys`), deletes the objects a thousand at a time, and only then empties the mailbox object. A failure leaves rows that can be deleted again, never an object no row names.
- **Proof today:** `test/workerd/original-routes.test.ts` and `test/workerd/original.test.ts` (the original: a reader is served and a non-member gets 404 on both routes, 401 without a session; a message id of another mailbox the caller is also a member of is 404; no answer of the message, list, thread, search and original routes contains `raw_key`, `auth_results` or the key itself; a sent message, a draft and old mail answer `NO_ORIGINAL`, a row whose object is gone `ORIGINAL_MISSING`; after deleting a message for good, emptying Trash and deleting the mailbox the bucket holds nothing of it, an arrival's object included; a bucket that fails leaves the rows; the migration is run from the release before it and rewrites nothing); `test/workerd/bulk.test.ts` (acting on many conversations: a reader is refused and a non-member told nothing on all three routes; a message, a label and a deed of another mailbox do not exist here; over a limit, an empty filter, both or neither scope, an unknown change, and Sent or Drafts as a target are refused with nothing changed; ### B5. The agent and MCP

- **Crosses:** mail content into a model prompt, and tool calls from a model or an MCP client back into mailboxes.
- **Invariant:** both are off unless `AGENT_ENABLED` or `MCP_ENABLED` is exactly `"true"`. They hold the caller's rights only, and less when the key says so. Neither can send or forward: the only way mail leaves is a person sending a draft in the UI. An MCP request is authenticated by its own key and never by a browser session; a mailbox a key cannot reach looks exactly like one that does not exist. Mail content given to a model is data, never instructions; the injection scan is advisory. Tests and local development never call a model.
- **Code today:** `workers/lib/features.ts` and the gates in `workers/app.ts`: the assistant's connection needs the app's own origin on a WebSocket handshake and on anything that changes (`sameOrigin`; a browser sends the cookie with a handshake from any page of the same site), then a session and the right to change mail in the mailbox it names (`mailboxDecision`). MCP (`workers/mcp/server.ts`) is stateless: `workers/app.ts` resolves `Authorization: Bearer pbk_…` to a key that is neither revoked nor expired and whose owner is still admitted (`workers/auth/keys.ts`), and a server is built for that one request. Every tool call reads the key's mailboxes joined with its owner's memberships again (`keyMailboxes`), so losing a membership or deleting a mailbox takes effect on the next call; a tool that changes anything also needs `keyAllows` (a write key and a role of owner or sender). Keys are made from the person's own memberships only (`workers/routes/keys.ts`), stored as a SHA-256 digest with a four-character hint, shown once, capped per person, optional expiry, creation and revocation audited. The handler allows only the request's own hostname as a browser Origin and sends no CORS headers. The assistant's tools (`workers/agent/tools.ts`) run with `withoutSend(env)`, an environment whose send binding refuses, so no tool can send whatever the model asks; they only save drafts. The automatic draft (`workers/agent/auto-draft.ts`) scans the sender, the subject and the body before any of it reaches the chat model, and fails closed: only a clear NO passes. Fixed rules follow every system prompt, including a mailbox's own (`workers/agent/prompt.ts`). Every model id is in `workers/lib/models.ts`. The tools shared by both (`workers/lib/tools.ts`) contain no function that sends; MCP runs them with `withoutSend(env)` as well. **What a tool answers about a message is built from a list of named fields** (`TOOL_MESSAGE_FIELDS`, `TOOL_LINE_FIELDS`, `TOOL_FILE_FIELDS`; ADR-0015, decision 21), so a new column of the mailbox's database does not reach a model or a client by itself. No tool returns the original of a message, its text, its key, its size, whether it has one, or what the platform said about its authentication, and no tool downloads; `raw_headers` stays in the answers as before.
- **Proof today:** `test/unit/features.test.ts`; "optional features are off by default" in `test/workerd/inbound.test.ts`; `test/workerd-agent/gate.test.ts` (with both features on: a handshake from another origin, a sibling host or no origin answers 403 before the session is looked at; 401 without a session, 404 to a non-member and to an administrator without a membership, 403 to a reader, a crafted mailbox name refused, MCP answering 401 to every role's session); `test/workerd-agent/mcp.test.ts` (no key, a made-up key and a session are refused; the token is not in D1 or in the key list; a key cannot be made for a mailbox its maker is not a member of, whatever their instance role; the tool list has no send, forward or delete; out-of-scope, missing and crafted mailbox ids give one identical error; a read-only key and a reader's write key change nothing; a sender's write key saves a draft and Sent stays empty; `update_draft` refuses a message that is not a draft and saves a draft as given, without a model; no move to Sent; membership removed, key revoked, key expired and mailbox deleted each stop the key at once; answers are `no-store` with the security headers and no CORS header); `test/unit/keys.test.ts`; `test/unit/agent-no-send.test.ts` (a model that asks to send reaches no send binding, and Sent stays empty); `test/unit/agent-ai.test.ts`, `agent-auto-draft.test.ts`, `agent-prompt.test.ts` and `agent-models.test.ts`, all against the fake model in `test/helpers/fake-ai.ts`. Labels through a key: `list_labels` reads, `label_email` needs a key and a membership that may change the mailbox, a label of an unreachable mailbox is refused without naming it, and no tool makes, renames or deletes a label (`test/workerd-agent/mcp.test.ts`). The assistant has the same two label tools and no more (`test/unit/agent-no-send.test.ts`: a label that is not one, a label of no mailbox and a message that is not there are each refused). The original (ADR-0015, decision 21): `test/workerd-agent/mcp.test.ts` pins the fields of `get_email` and of a list line for a message that has an original, and finds neither the key, the size, `has_original`, `unparsed`, the platform's field nor a byte of the original in the answers of `get_email`, `get_thread`, `list_emails` and `search_emails`; `test/unit/agent-no-send.test.ts` does the same for the assistant's tools, with a column added to the row that must not come through. No tool acts on many conversations (ADR-0014, decision 22): the routes of `workers/routes/bulk.ts` are reached over HTTP with a session only, and the tool lists the tests pin did not change.
- **Open:** MCP has keys only: OAuth 2.1 with a consent screen and per-tool grants is not built (ADR-0004); there is no per-key rate limit and no audit record per call; a key is a bearer secret, so a leaked key works until it is revoked or expires. Mail read through MCP is not scanned, so a hostile message can talk a client into moving mail to Trash or saving a draft. In chat, mail read through a tool is not scanned, so a hostile message can still make the assistant move mail to Trash or discard drafts. The assistant has not been run against a real model since its model ids changed.

### B6. The outbound sender

- **Crosses:** `From`, recipients, headers, body and attachments from a caller to the `send_email` binding, and from there to the internet under the domain's reputation.
- **Invariant:** one send path. A message leaves only if `From` is an address of a mailbox the caller may send as, and the per-mailbox and per-instance caps allow it. The real binding is reachable only through the adapter. Tests and local development never send real mail.
- **Code today:** `validateSender` in `workers/lib/email-helpers.ts`; `workers/email-sender.ts`; the send, reply and forward routes; the per-mailbox cap `checkSendRateLimit` in the Durable Object.
- **Proof today:** `test/unit/sender.test.ts` (`From` must be the mailbox's own address). One function stores and sends a person's message (`workers/lib/outgoing.ts`), for sending, answering and forwarding; `test/workerd/draft-files.test.ts` shows that a send names a draft of this mailbox or nothing is sent, and `test/unit/sending-limits.test.ts` that the request carries no files of its own. `test/workerd/vitest.config.ts` sets `remoteBindings: false`, so no test can send.
- **Open:** the single send function with its static check, the per-instance cap, the outbound queue with an idempotency key. The per-mailbox cap is tested in `test/workerd/sending-limit.test.ts`; the tools in `workers/lib/tools.ts` only save drafts (B5).

### B7. The setup and operator tokens

- **Crosses:** the setup token (the first-owner call) and the deploy token (operator calls), from the person who deployed or an installer acting for them.
- **Invariant:** these are not user credentials. They authorise a short, documented set of calls and never return message content. The health answer shows version and schema state only. The Worker holds bindings only: no Cloudflare account credential, no call to a Cloudflare REST API, no call home. No secret is in the repository, a fixture, a log or a snapshot.
- **Code today:** the setup token is built: it guards the first-owner call and the operator's recovery call (`workers/routes/account.ts`). There is no deploy token and no health route. `.dev.vars.example` holds placeholders only. `scripts/checks/account.ts` and `scripts/checks/secrets.ts` guard the two rules that already apply.
- **Proof today:** `pnpm static account` (shipped code and the Worker configuration name no Cloudflare API host and no credential variable) and `pnpm static secrets` (no credential shape, no tracked environment file), with their tests in `test/unit/checks-more.test.ts`. The secrets check is a net: a secret in an unknown format passes.
- **Open:** the tokens themselves, the closed-instance test (S10), the health route and its test, a scan over test output (S6).

### B8. Queues and exports

- **Crosses:** queue messages (inbound pointers, outbound sends, delivery events, the dead-letter queue), and export archives in R2 with their download links.
- **Invariant:** every consumer declares who may produce for it and validates each message with a schema. A queue message carries pointers and opaque ids, not mail. Parsing happens only in the inbound consumer. An export is made only for someone who may read the mailbox, after step-up; it is stored under the mailbox's prefix, served as a download, audited, and removed with the mailbox.
- **Code today:** not built. `wrangler.jsonc` binds no queue and there is no export code.
- **Proof today:** none.
- **Open:** everything; lands with milestones 2 and 3.

### B9. Dependencies and original work

- **Crosses:** every package version with its install scripts and licence, every file copied from the seed, and third-party text such as the vendored skill.
- **Invariant:** exact pins, at least three days old, installed from a frozen lockfile; build scripts approved one by one. Licences from the allow-list; no AGPL or GPL. No code, schema, test, text, translation or asset from any other mail product, and none named. Every seed file is listed in `copies.json`. The vendored skill is byte-identical to its manifest.
- **Code today:** `scripts/pins.ts`, `scripts/checks/licences.ts`, `names.ts`, `copies.ts`, `vendored-skills.ts`; `minimumReleaseAge` and `allowBuilds` in `pnpm-workspace.yaml`.
- **Proof today:** `pnpm static pins`, `licences`, `names`, `copies`, `vendored`; `test/unit/pins.test.ts`, `test/unit/checks.test.ts` (licences, names), `test/unit/vendored-skills.test.ts`; CI installs with `--frozen-lockfile`; `.github/dependabot.yml` opens weekly update pull requests.
- **Open:** a unit test for the `copies` check, the vulnerability audit job (S15), the scheduled job that fails on a pin more than one major behind (V2).

### B10. CI and releases

- **Crosses:** pull requests from forks, workflow tokens, and the artefact a deployer installs.
- **Invariant:** actions are pinned by commit. Tokens are least-privilege. A fork pull request gets no secret. CI runs `pnpm check`, the same command as a contributor. Security-sensitive paths have code owners; `main` is protected. A release is built once, attested and signed, and needs a current audit record.
- **Code today:** `.github/workflows/checks.yml` (read-only token, pinned actions, no secret, no persisted credentials) and `.github/CODEOWNERS`.
- **Proof today:** review only. No check reads the workflow yet.
- **Open:** the workflow lint, repository settings in a checked file, and the whole release side: the workflow, signing, attestation and the audit-record gate.

### B11. Where the project hosts things

- **Crosses:** the browser's same-site line. Every subdomain of one registrable domain is the same site, so a Podbay instance shares cookies' site scope and same-site requests with its neighbours. A test mail domain also shares a domain's sending reputation.
- **Invariant:** no running Podbay instance is served from `cloudhal.com` or a subdomain of it ([ADR-0003](../../../docs/adr/0003-project-home-on-cloudhal-dev.md)). The project's site, demos, trial instances and test mail domains live under `cloudhal.dev`. Cookies are host-only.

## 3. Guidance mode: a normal change

Use this for every change that touches a boundary, and for any security question or review.

1. **Name the boundaries.** Use the table in section 1. Say them in the pull request.
2. **Load the vendored skill** and stay in its guidance mode: the relevant parts only. No six phases, no output directory, no report files.
3. **Pick the companion files** that match the boundary:

   | Boundary | Read with `ATTACK-CLASSES.md` |
   |---|---|
   | B1, B8 | `PROTOCOLS-RPC-AND-MESSAGING.md`, `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md` |
   | B2 | `CLIENT-SIDE.md` |
   | B3 | `WEB-PROTOCOL-AND-AUTH.md` |
   | B4, B8 (exports, deletion) | `DATA-ISOLATION-AND-LIFECYCLE.md` |
   | B5 | `AI-AND-LLM.md` |
   | B6 | `WEB-PROTOCOL-AND-AUTH.md`, `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md` |
   | B7, B11 | `CLOUD-AND-DEPLOYMENT.md` |
   | B9, B10 | `SUPPLY-CHAIN-AND-RELEASE.md` |

4. **Apply it to the diff.** For each boundary, write down who the lower-trust party is, what they control, which control is meant to stop them, and what they would reach if it failed. If you cannot name all four, you have not understood the change yet.
5. **Add a regression test for each boundary touched.** The rules for that test are below.
6. **Keep this file true.** If the change adds a proof, moves code or closes an open item, update section 2 here and section 1 of [`docs/status.md`](../../../docs/status.md) in the same change.
7. **Run** `pnpm check` and `pnpm test:workerd`, and `pnpm e2e` when the change can be seen in a browser.

A regression test counts when all of these hold:

| It must | Why |
|---|---|
| Fail when the guard is removed | A test that passes either way proves nothing. Check it once by hand |
| Attack the boundary, not the happy path | A non-member, a forged header, a hostile file name, a foreign `From` |
| Run in the tier that can prove it | Pure helpers in `test/unit/`; handlers, bindings and Durable Objects in `test/workerd/` |
| Use values made for the test | No real address, no real mail, no secret, in the test or its snapshot |
| Be named in the pull request | The template asks which test covers the boundary |

If the boundary's code is not built yet, the rule still binds: a change in that area must not make the accepted rule harder to meet.

**If you find a vulnerability** while working, in your change or in existing code: do not describe it in a public issue, pull request or commit message. Follow [`SECURITY.md`](../../../SECURITY.md).

## 4. Full audit

A full audit is the vendored skill's **full audit mode**: all six phases, written artefacts, validated findings. How it is started and finished in this repository is the [`podbay-audit`](../podbay-audit/SKILL.md) skill.

| When | Scope |
|---|---|
| Before v0.1 | The whole repository |
| Before every release that changes a boundary | The whole repository, at the release commit. A release changes a boundary when its diff touches a path in section 1 or a rule in the security table |
| Every quarter | The whole repository, at the tip of `main` |

Run it with the `standard` or the `deep` profile. A `quick` or scoped run is partial coverage by the vendored skill's own definition; it is useful, and it does not count as a full audit.

### Where it may run

**Locally, with every binding local. Nowhere else.**

| Allowed | Never |
|---|---|
| Reading source | A real Cloudflare account, token or binding |
| `pnpm check` | `wrangler deploy`, a remote or preview binding, remote development |
| `pnpm test:workerd` (its config sets `remoteBindings: false`) | Sending real mail, to any address |
| `pnpm dev` with simulated mail, on loopback | Calling a real model: the agent stays off, or the `AI` binding is replaced by a fake |
| Fixtures and principals made for the run | A deployed Podbay, anyone's: a demo, a trial instance, a user's installation |
| | Real mailboxes, real messages, real addresses, real secrets |

The vendored skill's own execution rules also apply in full: a sandbox with no outside network, an empty environment, dummy principals. If the sandbox it requires is not available, do not run target code. Record the question as `needs_validation` with a safe plan.

### What it produces

1. The vendored skill writes its run directory **outside the repository** (by default under `~/security-audit-skill/podbay/`). Never commit it: it holds the detail of findings that may not be fixed yet, and this repository is public.
2. Both vendored validators pass on the run: `validate-findings.cjs` and `validate-coverage-ledger.cjs`.
3. A record goes to `docs/security/audits/`, from the template in [`docs/security/README.md`](../../../docs/security/README.md).
4. Each confirmed finding becomes a private advisory ([`SECURITY.md`](../../../SECURITY.md)). The public record names it by id, boundary, severity and status. The detail is added after the fix is released.
5. Each fix ships with a regression test, like any other boundary change.

## 5. The release gate

**A confirmed critical or high finding that is open blocks the release.**

| Question | Answer |
|---|---|
| Whose severity? | The vendored skill's anchors. The four outcomes at the top of this file are critical for Podbay. When the two differ, take the higher |
| What closes a finding? | The fix is merged with its regression test, and a fresh check confirms it. Or a fresh check rejects the finding with evidence. Both are written in the record |
| Is there a waiver? | No. Releasing with an open critical or high finding means changing rule S18 first, in the open, together with its check |
| Medium and lower? | They do not block. The record gives each an owner and a status |
| `needs_validation`? | It has no severity and does not block alone. The record states the missing fact and who resolves it |
| What is a current audit record? | A full-audit record whose commit includes the release's last boundary change, and that is less than one quarter old |
| Who checks the gate? | The project lead, by hand, until the release workflow exists. The workflow will then require the record (rule S18) |

## 7. Never

- **Never edit a file in `.claude/skills/security-audit/`**, and never add one. Podbay specifics belong in this file. To update the skill, replace the whole directory from upstream at a new commit, refresh `vendored.json` (commit, date, every hash), run its own tests with `node --test .claude/skills/security-audit/*.test.cjs`, and do nothing else in that change.
- Never run audit code against a real Cloudflare account, and never send real mail.
- Never put a real secret, a real message or a real address in a test, a fixture, a snapshot or a record.
- Never publish the detail of a finding before its fix is released.
- Never write "proof today" for a test that does not exist yet.
- Never skip a rule silently. Raise it with the rule id, the need and a proposal, and change the rule together with its check.
