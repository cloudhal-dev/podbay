# Podbay security

Podbay stores and shows other people's mail, inside the user's own Cloudflare account. Four outcomes are critical here ([`SECURITY.md`](../../../SECURITY.md)): reading a mailbox without a membership, sending as someone else, running script from a message, and leaking a credential.

This skill is the Podbay half of rule S18 ([engineering rules](../../../docs/engineering-rules.md)). It says **what** must hold: the trust boundaries, their invariants, the rules that guard them and the proof that exists today. The **method** (how to hunt, validate and report) is Cloudflare's [`security-audit`](../security-audit/SKILL.md) skill, vendored next to this one.

| Skill | Holds | Edited here |
|---|---|---|
| `.claude/skills/security-audit/` | The audit method, severity anchors, report schema and validators. MIT, from Cloudflare | **Never.** `pnpm static vendored` compares every file with `vendored.json` |
| `.claude/skills/podbay-security/` (this file) | Podbay's boundaries, invariants, cadence, release gate, records | Yes, in the same change that moves a boundary or adds a proof |

The rule in one paragraph: a change to a boundary ships a regression test. A full audit runs before v0.1, before every release that changes a boundary, and every quarter. A confirmed critical or high finding blocks the release. Records live in [`docs/security/`](../../../docs/security/README.md).

## 2. The trust boundaries

State on 2026-11-17: accounts, sign-in, memberships, the MCP keys, the content policies and the attachment rules are built and tested. Queues, exports and releases are **not built yet**; their rows say so. The original of a received message is kept in R2 since ADR-0015 was built on 2026-11-17. Since ADR-0016 was built on 2026-11-18, a message that is sent waits in the mailbox and leaves from the mailbox object's alarm, by one function. Since ADR-0008 was built on 2026-11-18, a mailbox has rules that run when mail arrives (filters, blocked senders) and an automatic reply, the one mail that leaves with nobody pressing Send. No full audit has run yet. Do not read a planned control as a control that exists.

### B1. Inbound mail bytes

- **Crosses:** a raw message from anyone on the internet, through Email Routing into the `email` handler. Envelope, headers, body, attachments and file names are all written by the sender.
- **Invariant:** the envelope recipient picks the mailbox, never a header. Nothing from a message becomes a Durable Object name or an R2 key without passing `workers/lib/inbound.ts` or `workers/lib/filenames.ts`. Parsing happens in one place, with size and time bounds, and its output is validated before it is stored. Logs carry opaque ids, never a body, a subject or an address.
- **Code today:** `mailboxAddressFor` and `routeInbound` in `workers/lib/inbound.ts`; `storageFilename` in `workers/lib/filenames.ts`; `shared/log.ts`, the only module that writes logs. **Arrival** (ADR-0015; `receiveEmail` in `workers/arrival.ts`, `workers/durableObject/originals.ts`): the mailbox is picked by the envelope before a byte is read; a declared size outside 1 byte to 25 MiB is refused with `setReject`; a row in `arrivals` is written, then the bytes are stored exactly and without metadata under a key made from 16 random bytes (`newRawKey` in `workers/lib/original.ts`), which holds nothing of the message; a stream of another length than declared is a failure that removes what was written and makes the handler throw. That is the line: after it the handler neither throws nor rejects. The message is parsed inside the handler, once; one transaction writes the message's row with the key and the size read from the arrival's own row, its attachment rows (marked `uploading_since`) and removes the arrival; then the files' bytes are written. A message the parser refuses, or whose text is too large for a row, is filed with its original alone (`unparsed`), joins no conversation and wakes no assistant. An arrival older than fifteen minutes is taken up by the next one, three at a time, each by a call that counts the attempt: parsed on the first, filed as `interrupted` from the second, removed when its bytes are not there. **Authentication** (`platformStatement` in `workers/lib/original.ts`): the first `Authentication-Results` field is read from the message's headers, cut at the first comma outside a quoted string or a comment, and kept only when its identifier is exactly `mx.cloudflare.net`; it is stored and, until the live check of decision 19 is recorded, said to nobody (`AUTHENTICATION_SHOWN` in `shared/original.ts`). **Known addresses** (ADR-0012): nothing on the way of incoming mail writes to `known_addresses`. A mailbox learns an address in one step, `learn` in `workers/durableObject/known.ts`, which the mailbox object calls only where it stores a message a person sent; an arriving message is filed by `fileArrival`, which does not pass it. **Rules** (ADR-0008; `shared/rules.ts`, `workers/lib/rule-facts.ts`, `workers/durableObject/rules.ts`): a mailbox's filters and blocked senders run once, in the step that files an arrival, after the message was parsed and before its row is written. What they are told of a message is built in one place (`factsOfParsed`) and cut to fixed lengths (`FACT_LIMITS`): the address and name it says it is from, the addresses of To and Cc, the subject, the first 20,000 characters of its text, whether a file came along, its `Auto-Submitted` field and whether it names a list. One pure function (`evaluate`) goes from the rules and those facts to an outcome. A condition is text compared after folding case, with `===` and `includes`: nothing a stranger or a person wrote becomes a regular expression, a `LIKE` pattern or part of a statement, and every query of the module is a constant with bound values. A rule that cannot be evaluated is skipped and counted; the function does not throw, and what surrounds it is guarded (`outcomeFor`), so a rule can change where a message is filed and can never stop it from being stored. A label is given only when it is a label of this mailbox and the place is neither Spam nor Trash.
- **Proof today:** `test/unit/rules.test.ts` (the vocabulary, the order, each kind of broken rule, hostile text in bounded time, the facts of a parsed message) and `test/workerd/rules.test.ts` (mail filed by a filter and by a block; a wildcard and a statement in a rule and in a message are words; a stored rule that is not one, and the rules table gone, leave the message stored, nothing rejected and nothing thrown; nothing runs on stored mail). `test/unit/inbound.test.ts`, `test/unit/filenames.test.ts`, and `test/workerd/inbound.test.ts` (the `To` header cannot pick a mailbox; a message without `To` is delivered; unknown and malformed recipients are rejected and nothing is stored). `test/unit/log.test.ts` (an address in a log field is masked); `pnpm static ratchets` counts `console.*` calls outside the log module. **Conversations:** `In-Reply-To` and `References` are the sender's claim. A message joins a conversation only when a message with one of those ids is in the mailbox and has the same subject (`workers/durableObject/threads.ts`; `test/workerd/inbound.test.ts`: joins, is refused with another subject, keeps answers to unknown mail together, survives 400 references). **Arrival** (`test/workerd/original.test.ts`): the object equals what was sent byte for byte, also when it is not text, and has no metadata; the key matches its shape for a message full of path characters; the arrival's row is there when the bytes are written and a file's row when its bytes are; a size outside the limits is rejected and the stream is not read; a shorter or longer stream, and a bucket that fails, leave no row and no object and the handler throws; a message nested deeper than the parser goes, and one larger than a row, arrive as `unparsed` with the envelope sender and their originals; a handler stopped before filing leaves a row the next arrival finishes, a second attempt is filed as `interrupted`, a row without bytes is removed; the same message twice is two messages. **Authentication** (`test/workerd/original-routes.test.ts`, `test/unit/original.test.ts`): a second field with the platform's identifier is not taken, a first field with another identifier keeps nothing even when the platform's follows, and a quoted string or comment that never closes keeps nothing. **Known addresses** (`test/workerd/known-addresses.test.ts`): after mail arrives with a crafted From, Reply-To and Cc, in the inbox and moved to Spam, the mailbox's table is empty and the completion offers nothing for any of them; `test/unit/known-addresses.test.ts` holds that neither the arrival nor the originals module names the step, and that the mailbox object calls it in exactly two places.
- **Open:** the live check of decision 19 (a forged field sent to a real domain; until it is in the ledger nothing is said about authentication), and a development instance, where nothing checks authentication and a field the sender wrote is believed. The queue consumer as the only parser, the hostile-message corpus, the static check on the parser import, validation of parsed output, the test that feeds marked content through every handler and scans the log output, the CPU budget.

### B2. Mail HTML and attachments in the browser

- **Crosses:** a stranger's HTML, links, inline images, attachment bytes, file names and declared types, shown inside a signed-in session. This is the one place a stranger's bytes meet the reader's session.
- **Invariant:** one renderer. The body is sanitised, placed in a document with a strict content policy, and shown in a sandboxed frame without same-origin access. Remote content stays out until the reader allows it. No other code injects message HTML. An attachment is a download: `Content-Disposition: attachment`, `nosniff`, and a risky type needs an acknowledgement that the server enforces.
- **Code today:** `app/lib/mail-html.ts` and `app/components/EmailIframe.tsx`; `scripts/checks/html.ts`. **The frame's height** (`shared/mail-frame.ts`, #110): the stranger writes every height in a message, and a height can follow the frame's own, so following every report would let a message grow the frame without end. The frame's script reports the body's height when it changes, and stops when the message moves three times in a row right after the frame took its height, after 200 reports at any one width, or at 20,000 px; the message then scrolls inside the frame. The page holds the same count and height itself (`nextFrameHeight`), whatever the frame says, because the script runs beside the stranger's markup. Only the page changes the frame's width; a message can only make the page's scrollbar come and go, and a width seen before keeps its count. The page marks the frame element `data-sized` once its document stands at its size, for that document only: from the height message it already accepts from that frame, or 500 ms after the element's own `load` event. Nothing crosses for it that did not before, the browser tests wait for it (#43), and nothing in the app reads it. **Content policies** (`shared/security-headers.ts`): the page's (`PAGE_CONTENT_POLICY`, on the assets through `public/_headers`) starts from `default-src 'none'` and names only the app's own origin, plus three entries the mail frame needs because a `srcdoc` frame inherits its embedder's policy: the hash of the frame's sizing script (`shared/mail-frame.ts`), `'unsafe-inline'` styles and `https:` images. The frame's own policy stays narrower and decides whether a remote image loads. Everything the Worker answers carries `API_CONTENT_POLICY` (`default-src 'none'`, `sandbox`) and `Cross-Origin-Resource-Policy: same-origin`. **Attachments** (`shared/attachment-risk.ts`, the routes in `workers/index.ts`): always `Content-Disposition: attachment` with `headerFilename`, `nosniff`, and a type from a short list of inert ones or `application/octet-stream` (`servedContentType`), never the sender's. `attachmentRisk` names the kinds that are dangerous by design, by last extension, by declared type and by invisible characters in the name; for those a GET answers 409 and the bytes leave only through `POST …/download` with `{ acknowledged: true }`, which the guard accepts from the app's own origin only, and always as opaque bytes. Images a message embeds are fetched by the app and put into the body as `data:` URLs (`app/lib/attachments.ts`, `app/lib/inline-images.ts`): plain image kinds only, never SVG, with a size cap; the frame loads nothing from Podbay either. **The original of a message** (ADR-0015; `workers/routes/original.ts`): it is every byte a stranger sent, so it is never a page. `GET …/emails/:id/original` answers JSON with the first 256 KiB as text (UTF-8, U+FFFD for what is not, NUL dropped), read from the bucket by a ranged read. The bytes leave only through `POST …/emails/:id/original/download` with `{ acknowledged: true }`, which the guard accepts from the app's own origin only: always `application/octet-stream`, `Content-Disposition: attachment` and a name Podbay made (`originalFileName` in `shared/original.ts`: the day and the start of the id, nothing of the subject or the sender). There is no GET for the bytes and no range. In the app (`app/components/email-panel/OriginalMessage.tsx`, `app/lib/original-text.ts`) the text goes into text nodes of one preformatted block that is laid out left to right whatever it holds; a control character, and a character that changes the direction of text or takes no room, is drawn as a mark with its code point; nothing becomes markup or a link. Before the download the app says, in its own dialog, that the file holds the whole message with every attachment and names the ones that can do harm.
- **Proof today:** `test/unit/mail-html.test.ts` (active content removed, remote content removed and counted, links, the content policy, the script nonce); `pnpm static html` with its tests in `test/unit/checks-more.test.ts` (no HTML injection in the UI, only the mail frame sets `srcdoc`); `test/unit/filenames.test.ts` (a file name cannot break out of the header). `test/unit/content-policy.test.ts`: the page's policy names no host, no wildcard, no `eval` and one script hash; the hash is the SHA-256 of the script and the script is exactly what the mail document contains; the frame needs nothing the page does not allow; the API's policy allows nothing. `test/unit/frame-height.test.ts` and `test/unit/email-iframe.test.ts`: the page follows at most 200 reports at one width, a width seen before keeps its count, never above 20,000 px and nothing that is not a positive height, also when the frame reports without end; `test/e2e/frame-size.spec.ts`: a message is shown to its last line, heights in `vh`, `%` and `calc()` that follow the frame come to rest within those bounds and scroll inside it, late pictures make the frame tall enough, and the proxy answers only the `.test` host a test named. `test/unit/attachment-risk.test.ts`: the kinds, the last extension behind trailing dots, invisible characters, the type when the name hides it, the served types. `test/workerd/attachments.test.ts`: headers and bytes of safe files; every risky kind refused to a link (also with a query string) and handed over to the acknowledged POST as opaque bytes; the acknowledgement must be said, cannot come from another origin or from a request without one; a reader may download, a non-member is told nothing. `test/workerd/draft-files.test.ts`: a person's own uploaded file, and a file copied from another message, are served by the same routes and the same rules; a file is downloaded only under the message it belongs to; a risky file is copied into a draft only with the acknowledgement. **The original** (`test/workerd/original-routes.test.ts`): both answers carry the security headers and are never cached; the download is `application/octet-stream` with `nosniff`, its length and the name Podbay made, and equals what arrived byte for byte; without the acknowledgement, from another origin and without an origin it is refused; a GET on the download path gives no bytes, with or without the word in the address; a range is not honoured. `test/unit/original.test.ts`: the marks for control and direction characters, the file name for hostile ids and dates, a character the 256 KiB cut goes through.
**In a real browser** (`pnpm e2e`, the built app under its real headers in Chrome; `test/e2e/`): sixteen kinds of hostile message each run no script, contact no host (every connection the browser attempts goes to a recording proxy, so this covers the frame's own process), open nothing, leave nothing active in the frame and trip no policy there; the frame has an opaque origin and cannot read the app, cookies or storage; remote images load only after the reader asks and never over plain http; links open an ordinary window without an opener; the page's policy by itself blocks an inline script in a frame even with a valid nonce; attachments never render as pages. `original.spec.ts`: an original full of markup, a script, a link, an image address, a frame and direction marks is shown as characters, with no element of the message in the page and no link, runs nothing and requests nothing; the file is saved with the exact bytes and never opened; a link to the bytes gives none; a sent message offers neither. The frame's sandbox (`MAIL_FRAME_SANDBOX`) no longer allows moving the app's window. **Since 2026-11-17:** a resource address that is neither embedded data nor remote is removed in both modes (a relative address resolves against the app in a `srcdoc` frame), and quoted text at the end of a reply is folded into a `details` element inside the sanitiser's own pass, so the body is still parsed and written out exactly once (`test/unit/mail-html.test.ts`: both, and that what is inside the fold is cleaned). The one inline script also reports the height when a fold is opened; its hash in the page's policy changed with it, and `test/unit/content-policy.test.ts` holds the two together.
- **Open:** the browser tests run in Chrome only. The frame's count of moves is seen to engage at device scales 1, 1.25 and 1.5; the browser's own zoom is not tried, and where it left the frame a pixel off the height reported, only the counts of 200 reports and 20,000 px would stop a height that follows the frame. Attachment risk goes by name and declared type; nothing inspects content or scans for malware. The page's policy has `'unsafe-inline'` styles and `https:` images because the frame inherits it; serving the frame from its own origin would let the page drop both. S12 applies as soon as the server fetches anything for a message.

### B3. Sign-in, sessions and step-up

- **Crosses:** credentials, session cookies, invitation and recovery links and step-up proofs, from any browser.
- **Invariant:** the design in [sign-in and access](../../../docs/auth-and-access.md). Invitation only. A new instance is closed until the guarded first-owner call. Sessions are server-side; cookies are host-only, `HttpOnly`, `Secure`, `SameSite=Lax`. Sensitive changes need fresh proof. Every authentication route is rate-limited and answers uniformly. Every state-changing request is checked against the app's own origin.
- **Code today:** Better Auth on D1 (`workers/auth/options.ts`, tables generated into `migrations/0001_auth.sql` and checked by `node scripts/auth-ddl.ts --check`). Password sign-in with a 12-character minimum; rate limits counted in the database. Accounts cannot be created over HTTP: the sign-up endpoint is refused, and accounts are made on the server by the guarded first-owner call (`POST /api/setup/owner`, needs the `SETUP_TOKEN` secret, works once, compared in constant time). An account without an instance role is not admitted. Every request that changes state must carry the app's own `Origin` (`sameOrigin` in `workers/auth/middleware.ts`). Cloudflare Access is an optional outer layer; a half-configured Access refuses to run. **Second step and passkeys** (Better Auth's two-factor plugin and `@better-auth/passkey`, tables in `migrations/0005_second_step.sql`): an authenticator app with recovery codes, enabled with the password and a first code, secrets and codes stored encrypted; `workers/auth/options.ts` refuses trusted devices (`trustDevice`), codes by mail or text message, and any method but the app. A passkey is bound to the request's hostname, needs user verification and a resident key, and is a complete sign-in. **A code from the app is used once** (`workers/auth/used-codes.ts`, the last step of `beforeAuthEndpoint`): before Better Auth sees a code it is claimed for the person it is typed for, as a row of Better Auth's `verification` table whose primary key is an HMAC of the person and the code under the instance secret, kept for two minutes; a second request with the same code fails to write that row, in whatever isolate, and is answered as a wrong code. **Fresh proof (step-up)** has one definition (`workers/auth/fresh.ts`): the session signed in within `FRESH_SECONDS` (ten minutes), and signing in again replaces the session (`afterAuthEndpoint` deletes the one the browser held). Routes marked `fresh` in the route table are checked last in the guard, on the session read from the database; a route marked `sensitive`, where only some requests need fresh proof (saving a mailbox's settings, which needs it when forwarding changes), has its session read from the database as well, and `test/unit/fresh.test.ts` holds that only its code reads the flag; Better Auth's own endpoints that change how a person signs in are held to it in `beforeAuthEndpoint` (`FRESH_AUTH_PATHS`), and registering a passkey by the plugin itself with the same `freshAge`. Sign-in attempts are counted per `cf-connecting-ip`. **Recovery** (`workers/auth/recovery.ts`, `workers/routes/recovery.ts`, table in `migrations/0006_recoveries.sql`): a link is issued by someone else, never for oneself (`mayIssueRecovery`: an owner for anyone, an administrator for members only), with fresh proof; the operator issues one for an owner with `SETUP_TOKEN`, compared in constant time (`POST /api/setup/recovery`). A link is 256 random bits, stored as a digest, good for a day, and a new one replaces the old. Redeeming it is one D1 batch whose later statements run only if the first marked the link used: new password hash, every session deleted, authenticator app and passkeys deleted, program keys revoked, audit row. It signs nobody in and never shows an old credential. **A person's choices** (ADR-0012; `migrations/0007_user_choices.sql`, `workers/auth/choices.ts`, `workers/routes/choices.ts`): `GET` and `PUT /api/v1/me/choices` have the right `session` and take the person from the session only; no id is in the path, the query or the body, so nothing points at someone else. The body is read up to 4 KiB and no further, then held to the strict schema (`shared/choices-schema.ts`): a key or a value it does not know refuses the whole change. The merge is one statement. The Worker stores the choices and decides nothing by them: not access, not what a list returns, not what is sent. A recovery link leaves them; the row goes with the account. **A route that opens a WebSocket** (ADR-0013) has a mark of its own in the route table, `upgrade`, and the guard is stricter for it than for a read, in this order: the request must be a WebSocket upgrade (426); its `Origin` must be the app's own, so one that is missing, `null`, another site's or a sibling host's is refused (403) before a session is looked for, with one answer whoever asks (`upgradeRefusal`: a handshake is a GET, a browser sends the cookie with it from any page of the same site, and a program has no `Origin` and so no way in); and the session is read from the database, as for a route marked `fresh`, so one that was ended a moment ago opens nothing. The proof is the session cookie; nothing in the address is ever read as one. What is opened is good for five minutes: the mailbox object keeps the time the guard allowed it and closes an older connection before it sends anything, and the app comes back through the guard after about four. The object does not know sessions, so a session that ends stops being told at five minutes at the latest and can open nothing new; the app closes its connections before it signs out and the server does not rely on that. **Mail that outlives a session** (ADR-0016): someone who held a session for a short while can schedule mail up to a year ahead. ### B4. Per-mailbox authorisation

- **Crosses:** a mailbox, message or attachment id in a request, and the identity of the caller.
- **Invariant:** deny by default. One `authorize(actor, action, resource)` decides for every route, tool and connection, from one table. A non-member gets "not found". **Managing is not reading:** an owner or administrator without a membership cannot open a mailbox, and granting themselves one needs step-up, is audited and is visible to the mailbox's owners. An id from a request is resolved to an opaque id before it touches storage. Deleting a message or a mailbox removes its rows, its Durable Object data and its R2 objects.
- **Code today:** `authorize` in `workers/auth/authorize.ts` decides; `ROUTE_TABLE` in `workers/auth/route-table.ts` names the right of every API route; the guard in `workers/auth/middleware.ts` runs in front of all of `/api/*`, refuses a route that is not in the table, resolves the mailbox through the D1 index with the caller's membership, and names the Durable Object after the address stored in the index, never after the request. A non-member gets 404, whatever their instance role, with one exception that `authorize` names: `mailbox.members.read` and `mailbox.members.manage` are also allowed to an owner or administrator of the instance without a membership. The guard looks the mailbox up with the caller's membership or none (`mailboxFor`), sets the storage stub only when there is a membership, and lets `authorize` decide; so a manager reaches the member routes (`workers/routes/people.ts`) and the registry (`GET /api/v1/registry/mailboxes`: address, owners, member count) and nothing else. Every member change needs fresh proof and is recorded with whose membership, which role and in which capacity it was made (`membershipDetail`: `as: owner` or `as: manager`, `self:` for one's own); `memberHistory` reads that record back for the mailbox's owners, including a manager who added and removed themselves. A mailbox always keeps an owner. Deleting a mailbox purges its Durable Object and its attachments (`purge` in `workers/durableObject/index.ts`). The agent connection checks a session and the right to change mail in that mailbox (`mailboxDecision`). **One message moved** (`POST …/emails/:id/move`, `moveEmail` in the mailbox object): Sent is never a target, Scheduled neither a source nor a target, and Drafts takes only a message the mailbox wrote and that never left (`writtenHere` in `workers/durableObject/drafts.ts`: no Message-ID, header list, original or `unparsed`), which is how the app undoes deleting a draft; `test/workerd/move.test.ts`. **Many conversations at once** (ADR-0014; `workers/routes/bulk.ts`, `workers/durableObject/deeds.ts` and `deed-steps.ts`): three routes, each `mailbox.write` in the route table. The request is parsed by one schema the app takes its types from (`shared/bulk.ts`): it names no target but Inbox, Archive, Spam and Trash and no change but a move, read, a star and labels, so nothing in it deletes for good or sends. A filter is the search route's own conditions (`buildSearchConditions`) and is only counted by the request that names it; acting is a second call that names the deed, whose id is opaque and is looked up in the database of the mailbox the guard picked. What a deed changed is kept for an hour as ids, places and marks, never content, and goes row by row with a message that is deleted for good. A filter deed is written to the audit log when it starts and when it is undone (`mailbox.bulk`, `mailbox.bulk_undone`) with who, which mailbox, which change and how many, never the filter. **The original of a message** (ADR-0015): both routes are `mailbox.read` in the route table. The message id only looks a row up in the database of the mailbox the guard picked (`originalOf` in `workers/durableObject/originals.ts`), and the key of the object comes from that row and from nowhere else: no code builds the key of an original. `raw_key` and `auth_results` never leave the mailbox object in an answer about a message (`shownMessage`), which says `has_original`, `raw_size` and `unparsed`. **Deletion** (rule S13): objects go before rows. One function deletes a message (`deleteMessage` in `workers/lib/messages.ts`: its files, its original, then its rows); emptying a place names a batch and its objects, deletes the objects, then the rows of that batch (`workers/durableObject/emptying.ts`); deleting a mailbox reads the keys of every file, every original and every arrival (`allKeys`), deletes the objects a thousand at a time, and only then empties the mailbox object. A failure leaves rows that can be deleted again, never an object no row names. **Known addresses** (ADR-0012; `workers/routes/known-addresses.ts`): completing an address is part of writing, so `GET …/known-addresses?q=` and forgetting one need `mailbox.write`, and forgetting them all `mailbox.manage`, which is audited by the mailbox and a number, never an address. The query is 1 to 64 characters, compared with `substr` and never put into a pattern; the answer is at most 8 entries of id, address and name, with no paging, total, count or date. The addresses are in the mailbox's own database, so they are deleted with it. **A person's choices** are not a mailbox's and not a manager's: see B3. **The mailbox tells the open app** (ADR-0013; `workers/routes/live.ts`, `workers/durableObject/live.ts`, `shared/live.ts`): being told that a mailbox changed is a way of reading it, so `GET …/live` is `mailbox.read` in the route table: a reader listens, and someone without a membership is told 404 whatever their instance role. **Nothing on the connection is mail:** the object sends one shape, a version and four counters, built by `liveMessage` from the list of kinds and from nothing else, at most 256 bytes; what changed is read through the ordinary routes, each authorised as before. A rule's id only names a row in the database of the mailbox the guard picked. Every change is in the audit log with who, which mailbox and a number or a kind (`mailbox.rules_changed`, `mailbox.sender_blocked`, `mailbox.sender_unblocked`, `mailbox.auto_reply_changed`), never a condition, an address or the words of the reply. ### B5. The agent and MCP

- **Crosses:** mail content into a model prompt, and tool calls from a model or an MCP client back into mailboxes.
- **Invariant:** both are off unless `AGENT_ENABLED` or `MCP_ENABLED` is exactly `"true"`. They hold the caller's rights only, and less when the key says so. Neither can send or forward: the only way mail leaves is a person sending a draft in the UI. An MCP request is authenticated by its own key and never by a browser session; a mailbox a key cannot reach looks exactly like one that does not exist. Mail content given to a model is data, never instructions; the injection scan is advisory. Tests and local development never call a model.
- **Code today:** `workers/lib/features.ts` and the gates in `workers/app.ts`: the assistant's connection needs the app's own origin on a WebSocket handshake and on anything that changes (`sameOrigin`; a browser sends the cookie with a handshake from any page of the same site), then a session and the right to change mail in the mailbox it names (`mailboxDecision`). MCP (`workers/mcp/server.ts`) is stateless: `workers/app.ts` resolves `Authorization: Bearer pbk_…` to a key that is neither revoked nor expired and whose owner is still admitted (`workers/auth/keys.ts`), and a server is built for that one request. Every tool call reads the key's mailboxes joined with its owner's memberships again (`keyMailboxes`), so losing a membership or deleting a mailbox takes effect on the next call; a tool that changes anything also needs `keyAllows` (a write key and a role of owner or sender). Keys are made from the person's own memberships only (`workers/routes/keys.ts`), stored as a SHA-256 digest with a four-character hint, shown once, capped per person, optional expiry, creation and revocation audited. The handler allows only the request's own hostname as a browser Origin and sends no CORS headers. The assistant's tools (`workers/agent/tools.ts`) run with `withoutSend(env)`, an environment whose send binding refuses, so no tool can send whatever the model asks; they only save drafts. Since ADR-0016 the working send binding sits in the mailbox object, which every tool can reach, so a binding that refuses is no longer enough by itself: the same environment hands out a handle on a mailbox without the methods by which mail is sent (`SENDING_METHODS`: `submit`, `unsend`, `reschedule` and the alarm), however the handle is made. No tool sends later, sends now, takes back or changes a time: scheduling is sending. A tool reads Scheduled as it reads any place and changes nothing in it: the mailbox object itself refuses. The automatic draft (`workers/agent/auto-draft.ts`) scans the sender, the subject and the body before any of it reaches the chat model, and fails closed: only a clear NO passes. Fixed rules follow every system prompt, including a mailbox's own (`workers/agent/prompt.ts`). Every model id is in `workers/lib/models.ts`. The tools shared by both (`workers/lib/tools.ts`) contain no function that sends; MCP runs them with `withoutSend(env)` as well. **What a tool answers about a message is built from a list of named fields** (`TOOL_MESSAGE_FIELDS`, `TOOL_LINE_FIELDS`, `TOOL_FILE_FIELDS`; ADR-0015, decision 21), so a new column of the mailbox's database does not reach a model or a client by itself. A program's key opens no connection: the route takes a session from the app's own page. The assistant's own WebSocket is not changed by that record: it is not closed when a membership ends and has no five minutes. **The rules of a mailbox are not a tool's** (ADR-0008 says nothing of a tool, so there is none): the handle the tools get also refuses `getRules`, `setRules`, `blockSender`, `unblockSender`, `getAutoReply` and `setAutoReply`, and `beginArrival` and `fileArrival` (`RULE_METHODS`): filing an arrival is what the automatic reply answers, so a tool that could file one could make the mailbox send to an address of its choosing.

### B6. The outbound sender

- **Crosses:** `From`, recipients, headers, body and attachments from a caller to the `send_email` binding, and from there to the internet under the domain's reputation. Since ADR-0016 also a time: the request says when the message leaves, up to a year ahead, and it leaves with nobody at the screen. Since ADR-0008 also a stranger's message: with the automatic reply on, mail that arrives makes the mailbox send, to an address the stranger chose.
- **Invariant:** one send path. A message leaves only if `From` is an address of a mailbox the caller may send as, and the per-mailbox and per-instance caps allow it. The real binding is reachable only through the adapter. Tests and local development never send real mail. A message leaves at most once by Podbay's own doing, and the rules hold at the time of leaving, not of pressing.
- **Code today** (ADR-0016). **Sending is two steps.** A send route (`workers/lib/outgoing.ts`, for sending, answering and forwarding) checks the request (`SendEmailRequestSchema`, `validateSender`, the limits of a message, the caps for an ordinary send), stores the message in the place Scheduled with a `waiting` row in `submissions` and a time, and answers. It calls no sending service. **One function lets mail leave:** `leaveOne` in `workers/durableObject/leaving.ts`, run from the mailbox object's alarm, is the only code that reads the send binding and the only caller of the adapter (`workers/email-sender.ts`). It reads the message from the stored rows (`workers/lib/outgoing-message.ts`) and its files from the bucket; nothing of a request reaches it. **At most once:** the handover (`handOver` in `submissions.ts`) changes `waiting` to `sending` only if the row is still as it was read, counts the message against the caps in the same transaction, and is on disk before the service is called; a row that is `sending` is never handed over again by anything. No answer within 60 seconds, an error without a code, an answer without an id and a row found `sending` fifteen minutes after its attempt began are `failed` with `unknown`: the service takes no idempotency key, so a second handover would be a second message, and a person decides. **The answer decides:** `{ messageId }` is `sent`; three codes read as "not now" and are tried after 1, 5 and 15 minutes, 1 hour and 4 hours; every other code is final and brings the message back to Drafts with the code. **The rules at leaving** (decision 15), in this order: the mailbox is still in the index (else nothing leaves); the person who sent it still holds `mailbox.send` by `authorize`, and their account was not recovered since (`workers/auth/standing.ts`); `From` is still the mailbox's address; the message still fits; the caps allow one more (else it waits). A message 24 hours past its time does not leave. **The caps** (`workers/durableObject/sending.ts`) count what left, in `send_log`: a time and a kind, nothing of a message, not shortened by deleting or moving mail. **Taking back and a new time** (`workers/routes/sending.ts`) are writes in the same object that would send, so the two cannot both win; both need `mailbox.send`. **The alarm** (`workers/durableObject/alarm.ts`) is set by one function to the earliest of all times; the handler catches its own errors and always sets the next. **Logs** of a handover carry the mailbox's object id, the message's id, a state and a code, never the service's own words, which may hold an address. **Recording whom a message went to** (ADR-0012, decision 17): the mailbox records To, Cc and Bcc, except its own address, when the message has left, in `leaveOne`, once. It changes nothing that is sent and cannot fail a send: what cannot be recorded is skipped, counted and logged as a number. **The automatic reply** (ADR-0008; `workers/durableObject/auto-reply.ts`, `replyOwed` in `shared/rules.ts`): one object for the mailbox, saved by an owner with fresh proof. Whether a reply is owed is one pure function, asked in the step that files an arrival and only for a message that was read: the reply is on and inside its dates; the message was not filed in Spam or Trash, its sender is not blocked, and neither is the envelope sender, whatever `From` says; it has no `Auto-Submitted` other than `no`; it names no list and is not bulk mail; the mailbox's address is in To or Cc; the envelope sender is one whole address, not the mailbox's own, also not under a `+tag` (it is compared after `mailboxAddressFor`, the step that routes incoming mail), not `MAILER-DAEMON`, `owner-…` or `…-request`; that sender was not answered in seven days (`auto_reply_log`: an address and a time); and the reply's own caps (10 in an hour, 50 in a day) and the mailbox's have room. The reply goes to the envelope sender and nobody else, and is made of the person's own subject and words: nothing of the message that arrived is read where it is built, not even its id. It is not sent there: it is taken as a message that waits (`take`) and leaves by `leaveOne` like any other, which knows it by the `Auto-Submitted` entry of its own stored header list (only the reply writes one; a message taken back to Drafts loses it), hands it over with the kind `auto`, sends `Auto-Submitted: auto-replied`, teaches the mailbox no address, and removes it instead of returning it to Drafts when it does not leave. At leaving it is asked again whether the reply is still on, inside its dates and saved as it was: its `requested_at` is the `set_at` of the save it was made from, and a reply saved again since does not leave (`stillAnswers`), so no words of an earlier save leave. The standing asked is that of the person who saved it, as of the time they saved it, for `mailbox.manage`, the right saving it needs (`AUTO_REPLY_RIGHT`); a reply that does not leave for one of those, or another reason of the mailbox's, takes back its record that the sender was answered. The first that fails the saver's right marks that save as stopped (`stop`, a row of `rules` with the save's time), and `consider` makes nothing from a stopped save, so a stopped reply costs nothing per message that arrives; a new save removes the mark. While it waits, `unsend` and `reschedule` answer 404 for it (`mailboxOwn` in `submissions.ts`), so nobody makes it their draft or their send. The text and the HTML of the reply are taken together only when the text is the text of the HTML, and the settings screen never saves back an HTML body (`replyToSave` in `app/lib/auto-reply.ts`): it saves the words it shows, so nobody becomes the saver of markup they did not see. Turning it off empties `auto_reply_log`. A reply that cannot be made or recorded is not made; the message that arrived is stored either way. Only mail filed in the Inbox wakes the assistant (`Filing` in `workers/durableObject/rules.ts`, `finish` in `workers/arrival.ts`).
- **Proof today:** `test/workerd/auto-reply.test.ts`, `auto-reply-standing.test.ts` (ADR-0008, with a send binding of the tests: every refusal above with a message that really arrives; the one call it makes, field by field; marked content of the incoming message in no call and in no stored row; the caps of its own and the mailbox's; no known address; a refusal and a missing answer of the service leave no draft and no second try; the person who saved it taken out of the mailbox, lowered to sender, and their account recovered; a reply turned off or past its end while it waited; a waiting reply refused to `unsend` and `reschedule` by a sender and an owner; a text and HTML that disagree; fresh proof; the message and its file stored when the record cannot be written) and `test/unit/auto-reply.test.ts`. Each guard was taken out once and seen to fail its test (`docs/status.md`, section 3). `pnpm static sender` (`scripts/checks/sender.ts`: one reader of the send binding, one caller of the adapter, one caller of the handover; `test/unit/sending.test.ts` tries it against a second of each). `test/unit/sender.test.ts` (`From` must be the mailbox's own address). `test/workerd/sending.test.ts`, with a send binding of the tests that answers what it is told and counts every call: a send calls no service and the message waits in Scheduled; it leaves at its time and is in Sent with the service's id; the place and the state are held together through every change; a second alarm, three runs at once, a repeated request, a retry before its time and a row found `sending` hand nothing over again; no answer is `unknown` and never a resend; each "not now" code, each kind of final refusal, the six attempts and their times; a final failure returns the message to Drafts with its files and the reason; undo inside the window, after it, and by the state rather than the clock; send later, a new time, send now, cancel, and the limits. `test/workerd/leaving.test.ts`: each question at leaving and its reason, the 24 hours, the caps (counted in `send_log`, not freed by deleting or moving sent mail, holding a message and letting it go later in the order of the times, two messages never taking the last place), and the alarm (the earliest time, set again by every change and run, ten messages in a run, its own errors caught, set again at a wake). `test/workerd/sending-limit.test.ts` (the hour and the day in time). `test/workerd/sending-routes.test.ts` (a log line of every kind of end carries no word of the mail, no address and nothing the service said). `test/workerd/known-addresses.test.ts`: each of the three sending routes, with and without a draft, records its recipients once when the message has left and never the mailbox's own address; a message that waits, is taken back or is refused teaches nothing; with the table gone the message still leaves. `test/workerd/vitest.config.ts` sets `remoteBindings: false`, so no test can send. Each of the handover's guard, the "no answer" rule, the right at leaving and the refusal of a waiting message was taken out once and seen to fail its test.
- **Open:** what cannot be known: a handover the service took and whose answer was lost stands as `failed` with `unknown` until a person looks, and sending it again may send it twice (ADR-0016, decision 7). The per-instance cap. Delivery, bounce and complaint events, and settling an `unknown` from them. A notice for a person whose app is closed when a send fails. None of the service's refusals was seen on Cloudflare's network: they are tried with a send binding of the tests. The automatic reply (ADR-0008) was not seen on Cloudflare's network: that the service takes `Auto-Submitted` is from its documentation. A blocked sender and a filter go by the address a message says it is from, which the sender writes; and the reply goes to the envelope sender, which a stranger can forge, so a stranger can make a mailbox with the reply on send one message in seven days to an address of their choosing, with the owner's words and nothing of theirs, up to the reply's caps (the record sends it to the envelope sender, as RFC 3834 asks). Replying to all teaches every recipient, also one a stranger put in Cc (accepted in ADR-0012).

### B7. The setup and operator tokens

- **Crosses:** the setup token (the first-owner call) and the deploy token (operator calls), from the person who deployed or an installer acting for them.
- **Invariant:** these are not user credentials. They authorise a short, documented set of calls and never return message content. The health answer shows version and schema state only. The Worker holds bindings only: no Cloudflare account credential, no call to a Cloudflare REST API, no call home. No secret is in the repository, a fixture, a log or a snapshot.
- **Code today:** the setup token is built: it guards the first-owner call and the operator's recovery call (`workers/routes/account.ts`). There is no deploy token and no health route. `.dev.vars.example` holds placeholders only. `scripts/checks/account.ts` and `scripts/checks/secrets.ts` guard the two rules that already apply.
- **Proof today:** `pnpm static account` (shipped code and the Worker configuration name no Cloudflare API host and no credential variable) and `pnpm static secrets` (no credential shape, no tracked environment file), with their tests in `test/unit/checks-more.test.ts`. The secrets check is a net: a secret in an unknown format passes.
- **Open:** the tokens themselves, the closed-instance test (S10), the health route and its test, a scan over test output (S6).

### B8. Queues and exports

- **Crosses:** queue messages (inbound pointers, outbound sends, delivery events, the dead-letter queue), and export archives in R2 with their download links.
- **Invariant:** every consumer declares who may produce for it and validates each message with a schema. A queue message carries pointers and opaque ids, not mail. Parsing happens only in the inbound consumer. An export is made only for someone who may read the mailbox, after step-up; it is stored under the mailbox's prefix, served as a download, audited, and removed with the mailbox.
- **Code today:** not built. `wrangler.jsonc` binds no queue and there is no export code.
- **Proof today:** none.
- **Open:** everything; lands with milestones 2 and 3.

### B10. CI and releases

- **Crosses:** pull requests from forks, workflow tokens, and the artefact a deployer installs.
- **Invariant:** actions are pinned by commit. Tokens are least-privilege. A fork pull request gets no secret. CI runs `pnpm check`, the same command as a contributor. Security-sensitive paths have code owners; `main` is protected. A release is built once, attested and signed, and needs a current audit record.
- **Code today:** `.github/workflows/checks.yml` (read-only token, pinned actions, no secret, no persisted credentials) and `.github/CODEOWNERS`. The job `commits (form and sign-off)` runs `scripts/commits.ts` on the commits of every pull request, with the rules in `scripts/commit-form.ts`: a conventional subject and the author's sign-off (D12). It installs nothing, and the two commit ids reach it through the environment, where the script takes nothing but a range of two ids. The command runs however it is started and fails a range it read nothing in. It is the pull request's own copy of the script that runs. When the browser run fails, its traces (`test-results/`) are uploaded for seven days by `actions/upload-artifact`, pinned by commit; a trace holds only the throwaway instance's own data, and the run's secrets in `.e2e/` are not uploaded (`test/unit/e2e-traces.test.ts`).
- **Proof today:** `pnpm static workflows` (`scripts/checks/workflows.ts`, `test/unit/workflows.test.ts`): no `pull_request_target` or `workflow_run`, permissions that only read, actions pinned by commit and no image, `ubuntu-latest` only, the word `secrets` in no expression, no expression inside a `run:` script, checkouts without persisted credentials. Its reader knows a small part of YAML and refuses every line outside it, so a workflow cannot pass by being written unusually. It does not prove that a pinned id belongs to the repository it names, nor that no action runs an expression given in its `with:`; both are by review. The commit check has `test/unit/commits.test.ts`, which also refuses a range that is not two commit ids.
- **Open:** repository settings compared with their record by a check, and the whole release side: the workflow, signing, attestation and the audit-record gate.

## 3. Guidance mode: a normal change

Use this for every change that touches a boundary, and for any security question or review.

1. **Name the boundaries.** Use the table in section 1. Say them in the pull request.
2. **Load the vendored skill** and stay in its guidance mode: the relevant parts only. No six phases, no output directory, no report files.
3. **Pick the companion files** that match the boundary:

   | Boundary | Read with `ATTACK-CLASSES.md` |
   |---|---|
   | B1, B8 | `PROTOCOLS-RPC-AND-MESSAGING.md`, `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md` |
   | B2 | `CLIENT-SIDE.md` |
   | B3 | `WEB-PROTOCOL-AND-AUTH.md` |
   | B4, B8 (exports, deletion) | `DATA-ISOLATION-AND-LIFECYCLE.md` |
   | B5 | `AI-AND-LLM.md` |
   | B6 | `WEB-PROTOCOL-AND-AUTH.md`, `RESOURCE-EXHAUSTION-AND-AVAILABILITY.md` |
   | B7, B11 | `CLOUD-AND-DEPLOYMENT.md` |
   | B9, B10 | `SUPPLY-CHAIN-AND-RELEASE.md` |

4. **Apply it to the diff.** For each boundary, write down who the lower-trust party is, what they control, which control is meant to stop them, and what they would reach if it failed. If you cannot name all four, you have not understood the change yet.
5. **Add a regression test for each boundary touched.** The rules for that test are below.
6. **Keep this file true.** If the change adds a proof, moves code or closes an open item, update section 2 here and section 1 of [`docs/status.md`](../../../docs/status.md) in the same change.
7. **Run** `pnpm check` and `pnpm test:workerd`, and `pnpm e2e` when the change can be seen in a browser.

A regression test counts when all of these hold:

| It must | Why |
|---|---|
| Fail when the guard is removed | A test that passes either way proves nothing. Check it once by hand |
| Attack the boundary, not the happy path | A non-member, a forged header, a hostile file name, a foreign `From` |
| Run in the tier that can prove it | Pure helpers in `test/unit/`; handlers, bindings and Durable Objects in `test/workerd/` |
| Use values made for the test | No real address, no real mail, no secret, in the test or its snapshot |
| Be named in the pull request | The template asks which test covers the boundary |

If the boundary's code is not built yet, the rule still binds: a change in that area must not make the accepted rule harder to meet.

**If you find a vulnerability** while working, in your change or in existing code: do not describe it in a public issue, pull request or commit message. Follow [`SECURITY.md`](../../../SECURITY.md).

## 4. Full audit

A full audit is the vendored skill's **full audit mode**: all six phases, written artefacts, validated findings. How it is started and finished in this repository is the [`podbay-audit`](../podbay-audit/SKILL.md) skill.

| When | Scope |
|---|---|
| Before v0.1 | The whole repository |
| Before every release that changes a boundary | The whole repository, at the release commit. A release changes a boundary when its diff touches a path in section 1 or a rule in the security table |
| Every quarter | The whole repository, at the tip of `main` |

Run it with the `standard` or the `deep` profile. A `quick` or scoped run is partial coverage by the vendored skill's own definition; it is useful, and it does not count as a full audit.

### Where it may run

**Locally, with every binding local. Nowhere else.**

| Allowed | Never |
|---|---|
| Reading source | A real Cloudflare account, token or binding |
| `pnpm check` | `wrangler deploy`, a remote or preview binding, remote development |
| `pnpm test:workerd` (its config sets `remoteBindings: false`) | Sending real mail, to any address |
| `pnpm dev` with simulated mail, on loopback | Calling a real model: the agent stays off, or the `AI` binding is replaced by a fake |
| Fixtures and principals made for the run | A deployed Podbay, anyone's: a demo, a trial instance, a user's installation |
| | Real mailboxes, real messages, real addresses, real secrets |

The vendored skill's own execution rules also apply in full: a sandbox with no outside network, an empty environment, dummy principals. If the sandbox it requires is not available, do not run target code. Record the question as `needs_validation` with a safe plan.

### What it produces

1. The vendored skill writes its run directory **outside the repository** (by default under `~/security-audit-skill/podbay/`). Never commit it: it holds the detail of findings that may not be fixed yet, and this repository is public.
2. Both vendored validators pass on the run: `validate-findings.cjs` and `validate-coverage-ledger.cjs`.
3. A record goes to `docs/security/audits/`, from the template in [`docs/security/README.md`](../../../docs/security/README.md).
4. Each confirmed finding becomes a private advisory ([`SECURITY.md`](../../../SECURITY.md)). The public record names it by id, boundary, severity and status. The detail is added after the fix is released.
5. Each fix ships with a regression test, like any other boundary change.

## 5. The release gate

**A confirmed critical or high finding that is open blocks the release.**

| Question | Answer |
|---|---|
| Whose severity? | The vendored skill's anchors. The four outcomes at the top of this file are critical for Podbay. When the two differ, take the higher |
| What closes a finding? | The fix is merged with its regression test, and a fresh check confirms it. Or a fresh check rejects the finding with evidence. Both are written in the record |
| Is there a waiver? | No. Releasing with an open critical or high finding means changing rule S18 first, in the open, together with its check |
| Medium and lower? | They do not block. The record gives each an owner and a status |
| `needs_validation`? | It has no severity and does not block alone. The record states the missing fact and who resolves it |
| What is a current audit record? | A full-audit record whose commit includes the release's last boundary change, and that is less than one quarter old |
| Who checks the gate? | The project lead, by hand, until the release workflow exists. The workflow will then require the record (rule S18) |

## 7. Never

- **Never edit a file in `.claude/skills/security-audit/`**, and never add one. Podbay specifics belong in this file. To update the skill, replace the whole directory from upstream at a new commit, refresh `vendored.json` (commit, date, every hash), run its own tests with `node --test .claude/skills/security-audit/*.test.cjs`, and do nothing else in that change.
- Never run audit code against a real Cloudflare account, and never send real mail.
- Never put a real secret, a real message or a real address in a test, a fixture, a snapshot or a record.
- Never publish the detail of a finding before its fix is released.
- Never write "proof today" for a test that does not exist yet.
- Never skip a rule silently. Raise it with the rule id, the need and a proposal, and change the rule together with its check.
