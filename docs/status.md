- Companion to [`AGENTS.md`](../AGENTS.md), the [engineering rules](engineering-rules.md) and the [roadmap](roadmap.md).
- Question answered here: which rule is held by which check today, which is not yet, and what is knowingly left open.

**A rule without an automated check is not a rule.** Section 1 is the list of rules that have one. Add a row in the same change that adds the check; never describe a planned control as one that exists.

## 3. Known debt and known gaps

Debt from the seed, recorded in `ratchets.json` and the `overrides` of `biome.json`:

- Non-null assertions in the API routes, a few accessibility and hook-dependency findings in the UI.
- `workers/durableObject/index.ts` is above the 800-line limit.

Gaps that are open on purpose until their milestone, all behind features that are off by default or absent:

- **An owner or administrator of the instance can take any mailbox**: add themselves, even replace its owners. That is what managing memberships means; what stands against misuse is fresh proof, the audit log and the record the mailbox's owners can read. Nobody is told when it happens: an owner sees it only when they open the members page. The record is read from audit rows by the mailbox's address.
- **Recovery always needs a second person or the operator.** There is no self-service reset: Podbay cannot mail a link yet, and a recovery address outside Podbay is not built. Whoever issues a link decides, outside Podbay, that the person asking is who they say. Nobody is required to have a second step yet, not even owners.
- **The setup token is a standing credential once recovery exists**: whoever holds `SETUP_TOKEN` can take over an owner account through `POST /api/setup/recovery`. A deployer who does not want that removes the secret after setup and sets a new one only when an owner must be recovered; without the secret the call answers 503. Podbay's own public routes (setup, invitations, recovery) are not rate-limited; their tokens are 190 random bits or more, the setup token as strong as the deployer made it (24 characters at least).
- **A code from the authenticator app can be used again within its 30 seconds**; Better Auth does not remember used codes. Passkeys are tested with a software authenticator in the Workers runtime and with Chrome's own virtual authenticator in the browser tests, not with a physical device.
- Changing forwarding is checked for fresh proof on the session copy cached in the cookie (at most a minute old); the other sensitive routes read the database.
- **The assistant has not been run against a real model** since its model ids and SDK were updated: its logic is tested with a fake, never with Workers AI. In chat it can still be told by a hostile message to move mail to Trash or discard drafts; it cannot send.
- Storage is still named after the mailbox address and the message id, taken from the index and never from the request; opaque storage ids come with the storage work of milestone 3.

- **MCP clients sign in with a key, not with OAuth.** A key is a long-lived bearer secret that a person copies into their client; there is no consent screen and no per-tool grant, only read or read-and-draft per mailbox ([ADR-0004](adr/0004-mcp-keys-first.md)). MCP calls are not rate-limited per key yet, and only key creation and revocation are in the audit log, not each call. A hostile message read through MCP can still talk a client into moving mail to Trash or writing a draft; it cannot make it send.
- **The browser tests run in one browser, Chrome.** No other engine is tried. While the sanitiser parses a hostile message the browser reports two kinds of policy violation in the page (an event handler attribute, a `<base>`); they are reports about markup that is then removed, nothing ran, and the tests accept exactly those two. The page allows inline styles and `https:` images only because the mail frame inherits its policy; the frame's own policy is the one that keeps remote images out until the reader asks.
- **The Workers-runtime tests need one worker for each test file.** A worker of the test runner that is given a second file exits, and that file's tests do not run; with fewer workers than files the run fails (seen on 2026-11-17, when an eighth file was added on a machine that gave seven workers). Both configurations now ask for as many workers as there are files. The cause in the runner is not found.
- **The browser tests' recording proxy used to fall over.** When the browser dropped a connection that was being refused, the proxy exited on the unhandled error and every later test failed to reach it (seen several times on 2026-11-17, always as a whole run failing at once). It now ignores an error on one connection. A run that fails this way is the proxy, not the app.
- **A click into the mail frame can miss just after a message opens.** Twice on 2026-11-17, in full runs only, a test's click on something inside the frame did nothing (a link, the line that opens folded quoted text); alone the same tests pass every time. The two tests now click again when nothing happened. Whether a person can hit the same moment is not known; the cause is not found.
- **Attachment risk goes by the file's name and declared type.** Nothing looks inside a file and nothing scans for malware: a harmful file with an innocent name and type is an ordinary download. The marks say which kinds are dangerous by design, never that a file is safe.
- **The mail screens are not complete.** Undo covers moves (archive, spam, Trash, a folder), not a permanent delete, a send or a change of read state. Snooze is not built. Newer and Older step within the page of the list on screen, not across pages, and are not offered after a reload of an open conversation in a folder that has not loaded its list. A conversation is filed as one message: a move from the list moves the line's latest message, as before. Notes appear at the bottom right, where an open compose window can cover them.
- **Labels: what is left.** The limit of 50 conversations in one labelling request (ADR-0007, decision 11) bounds nothing today, because the route labels one conversation per request; labelling a selection is one request per conversation. The tree of labels in the rail cannot be folded.
- **Conversations formed before 2026-11-17 may still be split.** An incoming message now joins the conversation of the message it answers when that message is in the mailbox and has the same subject; before, the first message of a conversation that began with incoming mail was kept apart from its replies. Mail that is already stored was not regrouped.
- **Before ADR-0007, deleting a custom folder deleted its messages for good.** The mailbox's database enforces foreign keys (tried in the Workers runtime on 2026-11-17), so `ON DELETE CASCADE` did what it says, without Trash. The route is removed and custom folders became labels; no instance in use is known to have called it.
- **Languages: what is left.** The Turkish catalog (605 messages) was written with the code on 2026-11-17 and has not been read through by a second person. What the Worker says stays English: the reason a request was refused, and everything the assistant and the MCP tools answer. The built-in prompt of the assistant is English. `pnpm static messages` reads markup as text, so words handed to a toast or an error as a plain string are not caught by it; they were found once with a parser on 2026-11-17 and wired by hand.
- **Two owners saving a mailbox's settings at once lose one change.** The route that saves them replaces the whole object and raises `rev` without comparing it, and the app sends its cached copy with one key changed. Found on 2026-11-17 while reading for [ADR-0012](adr/0012-a-persons-choices-and-known-addresses.md); a compare on `rev` is a change of the route's contract and is not made yet.
- **Found by reading on 2026-11-17, while four records were written, and not corrected yet.** A message's files are written to the bucket before their rows, on arrival and on sending, so a failure in between leaves objects no row names. A send that the sending service refuses after the request was answered leaves its message in Sent though it was not sent; the request is now held to the service's own limits, which closes the known ways there, and the queue of milestone 3 closes the rest. The route that moves one message takes Sent and Drafts as a target, which the tools refuse; the app's Undo relies on it. The list of a place and the count beside it group old mail without a thread id differently. The list of a place reads every message of the mailbox for each page. `attachments` has no index on `email_id`. Each is named in the record that would close it ([ADR-0011](adr/0011-drafts-keep-their-files.md), [ADR-0014](adr/0014-acting-on-many-conversations.md)) or is rule D2's and D13's work.
- **Found by reading on 2026-11-17 for ADR-0015 and ADR-0016, and not corrected.** The sending caps count the messages that stand in Sent, so deleting or moving sent mail gives the allowance back, and two sends at once can both pass; the count needs a record of its own ([ADR-0016](adr/0016-outgoing-mail-waits-before-it-leaves.md)). The id Podbay stores for a sent message is not the `Message-ID` the recipient sees: the sending service makes its own and refuses one from the caller, so an answer to mail that started here joins its conversation by subject only, and "Show headers" on a sent message shows a date and an id that did not travel. The send runs after the request is answered and is cut off after 30 seconds, like a refused send it leaves its message in Sent. An incoming message whose text is larger than a row of the mailbox's database can hold is not stored, and its files stay in the bucket; one the parser refuses is not delivered ([ADR-0015](adr/0015-the-original-message-is-kept.md)). Nothing reads what the receiving service says about SPF, DKIM and DMARC, which the architecture describes as shown.
- **Emptying goes by the date of a message.** "What was there when it was asked" is decided by the date a message carries, which for incoming mail is the time it arrived. A message with an older date that is moved into Trash while Trash is being emptied goes with the rest.
- Search builds `LIKE` patterns from user text, and Durable Object SQL caps a pattern at 50 bytes; FTS5 replaces it in milestone 3.
