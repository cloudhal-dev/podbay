# Podbay: status

- Companion to [`AGENTS.md`](../AGENTS.md), the [engineering rules](engineering-rules.md) and the [roadmap](roadmap.md).
- Question answered here: which rule is held by which check today, which is not yet, and what is knowingly left open.

**A rule without an automated check is not a rule.** Section 1 is the list of rules that have one. Add a row in the same change that adds the check; never describe a planned control as one that exists.

## 3. Known debt and known gaps

Debt from the seed, recorded in `ratchets.json` and the `overrides` of `biome.json`:

- Non-null assertions in the API routes, a few accessibility and hook-dependency findings in the UI.

Gaps that are open on purpose until their milestone, all behind features that are off by default or absent:

- **An owner or administrator of the instance can take any mailbox**: add themselves, even replace its owners. That is what managing memberships means; what stands against misuse is fresh proof, the audit log and the record the mailbox's owners can read. Nobody is told when it happens: an owner sees it only when they open the members page. The record is read from audit rows by the mailbox's address.
- **Recovery always needs a second person or the operator.** There is no self-service reset: Podbay cannot mail a link yet, and a recovery address outside Podbay is not built. Whoever issues a link decides, outside Podbay, that the person asking is who they say. Nobody is required to have a second step yet, not even owners.
- **The setup token is a standing credential once recovery exists**: whoever holds `SETUP_TOKEN` can take over an owner account through `POST /api/setup/recovery`. A deployer who does not want that removes the secret after setup and sets a new one only when an owner must be recovered; without the secret the call answers 503. Podbay's own public routes (setup, invitations, recovery) are not rate-limited; their tokens are 190 random bits or more, the setup token as strong as the deployer made it (24 characters at least).
- **A code from the authenticator app is used once** since 2026-11-18 (issue #12): Podbay claims it before Better Auth sees it, in Better Auth's own `verification` table under a key made from the person and the code, for two minutes. A code is claimed whether it is right or wrong, so a right code refused for another reason (a locked account) waits for the next one, and a person who turned the app on a moment ago signs in with the app's next code. Better Auth itself still remembers no code: the guard is Podbay's (`workers/auth/used-codes.ts`) and must stay in front of the endpoint when Better Auth is updated. Passkeys are tested with a software authenticator in the Workers runtime and with Chrome's own virtual authenticator in the browser tests, not with a physical device.
- **The assistant has not been run against a real model** since its model ids and SDK were updated: its logic is tested with a fake, never with Workers AI. In chat it can still be told by a hostile message to move mail to Trash or discard drafts; it cannot send.
- Storage is still named after the mailbox address and the message id, taken from the index and never from the request; opaque storage ids come with the storage work of milestone 3. The original of a message is the one exception: its key is random and is read from its row ([ADR-0015](adr/0015-the-original-message-is-kept.md)).

- **MCP clients sign in with a key, not with OAuth.** A key is a long-lived bearer secret that a person copies into their client; there is no consent screen and no per-tool grant, only read or read-and-draft per mailbox ([ADR-0004](adr/0004-mcp-keys-first.md)). MCP calls are not rate-limited per key yet, and only key creation and revocation are in the audit log, not each call. A hostile message read through MCP can still talk a client into moving mail to Trash or writing a draft; it cannot make it send.
- **The browser tests run in one browser, Chrome.** No other engine is tried. While the sanitiser parses a hostile message the browser reports two kinds of policy violation in the page (an event handler attribute, a `<base>`); they are reports about markup that is then removed, nothing ran, and the tests accept exactly those two. The page allows inline styles and `https:` images only because the mail frame inherits its policy; the frame's own policy is the one that keeps remote images out until the reader asks.
- **The Workers-runtime tests need one worker for each test file.** A worker of the test runner that is given a second file exits, and that file's tests do not run; with fewer workers than files the run fails (seen on 2026-11-17, when an eighth file was added on a machine that gave seven workers). Both configurations now ask for as many workers as there are files. The cause in the runner is not found.
- **The browser tests' recording proxy used to fall over.** When the browser dropped a connection that was being refused, the proxy exited on the unhandled error and every later test failed to reach it (seen several times on 2026-11-17, always as a whole run failing at once). It now ignores an error on one connection. A run that fails this way is the proxy, not the app.
- **The Workers-runtime tests run four files at a time.** Each file needs a runtime of its own, and twenty and more started at once took more memory than an 8 GB machine has: on 2026-11-17 it came to a stop during a run. `scripts/test-workerd.ts` runs them in groups and adds up the totals; `PODBAY_WORKERD_AT_ONCE` changes the size of a group.
- **The Workers-runtime tests failed once as a whole, and it could not be made to happen again.** On 2026-11-17, right after a `pnpm check`, every file of `pnpm test:workerd` failed in its setup; the output was not kept. The same command passed four times afterwards, also straight after `pnpm check`. The cause is not known.
- **A click into the mail frame could miss just after a message opened.** Twice on 2026-11-17, in full runs only, a test's click on something inside the frame did nothing (a link, the line that opens folded quoted text). Made to happen at will on 2026-11-19: a single click made before the frame said its height missed 3 times in 20, and none missed once the frame had said it (#43). The frame now marks itself `data-sized` when it has, the browser tests' `openMessage` waits for that, and the two tests click once. Why such an early click is lost, and whether a person clicking in that first moment loses it too, is not known.
- **Attachment risk goes by the file's name and declared type.** Nothing looks inside a file and nothing scans for malware: a harmful file with an innocent name and type is an ordinary download. The marks say which kinds are dangerous by design, never that a file is safe.
- **The mail screens are not complete.** Undo covers what is done to conversations (a move, read, a star, a label), for an hour and from the mailbox's own record, and a send for the window the person chose ([ADR-0016](adr/0016-outgoing-mail-waits-before-it-leaves.md)); it does not cover a permanent delete. Snooze is not built. Newer and Older step within the page of the list on screen, not across pages, and are not offered after a reload of an open conversation in a folder that has not loaded its list. Notes appear at the bottom right, where an open compose window can cover them.
- **Acting on many conversations ([ADR-0014](adr/0014-acting-on-many-conversations.md)): what is left.** A deed on everything runs while its page is open: leaving stops it where it is (what was done stays done and can be taken back), and nothing finishes it unattended. Deleting for good is still one request for each ticked line of Trash, and takes the line's newest message only; emptying a label and deleting everything a search finds are not built. A draft is not moved by the new route: a draft deleted from the Drafts list still goes to Trash by the route for one message, with the app's own memory as its Undo, and "everything" is not offered in Drafts. With conversation view on, a search lists messages while a deed takes lines: a star or "unread" given from a search line goes to the newest message of that conversation in that place, which need not be the line that was pressed. "Move to" a label is not offered for everything a search finds across places. Undo is all or nothing for each message: one that was changed again in any way the deed had changed it is left as it is. The budget of one step is measured by the clock on a mailbox of 1,205 messages, not as CPU time, and a deed on a search by text reads every message it has not passed. A message without a date is never found by a filter deed.
- **Labels: what is left.** The tree of labels in the rail cannot be folded.
- **Conversations formed before 2026-11-17 may still be split.** An incoming message now joins the conversation of the message it answers when that message is in the mailbox and has the same subject; before, the first message of a conversation that began with incoming mail was kept apart from its replies. Mail that is already stored was not regrouped.
- **Before ADR-0007, deleting a custom folder deleted its messages for good.** The mailbox's database enforces foreign keys (tried in the Workers runtime on 2026-11-17), so `ON DELETE CASCADE` did what it says, without Trash. The route is removed and custom folders became labels; no instance in use is known to have called it.
- **Languages: what is left.** The Turkish catalog (910 messages on 2026-11-18, in the two files `app/i18n/tr.ts` joins) was written with the code on 2026-11-17 and has not been read through by a second person. What the Worker says stays English: the reason a request was refused, and everything the assistant and the MCP tools answer. The built-in prompt of the assistant is English. `pnpm static messages` reads markup as text, so words handed to a toast or an error as a plain string are not caught by it; they were found once with a parser on 2026-11-17 and wired by hand.
- **Two owners saving a mailbox's settings at once lose one change.** The route that saves them replaces the whole object and raises `rev` without comparing it, and the app sends its cached copy with one key changed. Found on 2026-11-17 while reading for [ADR-0012](adr/0012-a-persons-choices-and-known-addresses.md); a compare on `rev` is a change of the route's contract and is not made yet.
- **Found by reading on 2026-11-17, while four records were written, and not corrected yet.** A received message's files were written to the bucket before their rows, so a failure in between left objects no row names; that was corrected on 2026-11-17 when ADR-0015 was built: a row now comes before the object it names for an arriving message as for a draft. A send that the sending service refused after the request was answered left its message in Sent though it was not sent; that was corrected on 2026-11-18, when [ADR-0016](adr/0016-outgoing-mail-waits-before-it-leaves.md) was built: a message is in Sent when the service took it, and one it refused is in Drafts with the reason. The route that moves one message took Sent and Drafts as a target, which the tools refuse; that was corrected on 2026-11-18 (issue #31): Sent is never a target and Drafts takes only a draft. The list of a place and the count beside it group old mail without a thread id differently. The list of a place reads every message of the mailbox for each page. Each is named in the record that would close it ([ADR-0011](adr/0011-drafts-keep-their-files.md), [ADR-0014](adr/0014-acting-on-many-conversations.md)) or is rule D2's and D13's work.
- **Found by reading on 2026-11-17 for ADR-0015 and ADR-0016.** Two were corrected on 2026-11-18, when [ADR-0016](adr/0016-outgoing-mail-waits-before-it-leaves.md) was built: the sending caps counted the messages that stood in Sent, so deleting or moving sent mail gave the allowance back, and two sends at once could both pass; they now count what left, in a record of the mailbox's own, in the one object that sends. And the send ran after the request was answered and was cut off after 30 seconds; it now runs from the mailbox object's alarm, with nobody waiting for it. **Not corrected:** the id Podbay stores for a sent message is not the `Message-ID` the recipient sees: the sending service makes its own and refuses one from the caller, so an answer to mail that started here joins its conversation by subject only, and "Show headers" on a sent message shows an id that did not travel (its date is now the time it left). The service's own id is kept since ADR-0016 (`service_id` in `submissions`) and nothing reads it yet. Three more that were found then were corrected on 2026-11-17, when [ADR-0015](adr/0015-the-original-message-is-kept.md) was built: an incoming message whose text is larger than a row, and one the parser refuses, were not stored and are now messages with their originals; nothing read what the receiving service says about SPF, DKIM and DMARC, and it is now kept (not yet shown: see the next line); and a message was deleted rows first, its objects afterwards, where it is now objects first, for one message, for an emptied place and for a whole mailbox.
- **The original message ([ADR-0015](adr/0015-the-original-message-is-kept.md)): what is left.** Mail that arrived before 2026-11-17 has no original and never will: the bytes are gone. Sent mail and drafts have none either: the sending service builds what leaves. **The line about SPF, DKIM and DMARC is built and not shown.** Decision 19 asks for one message with a forged field of the platform's own identifier, sent by hand to a real domain, with what arrives recorded in the ledger; that needs a real domain and was not done. Until `runtime.email.authentication_results.forged` in the [ledger](cloudflare/ledger.json) is verified, `AUTHENTICATION_SHOWN` (`shared/original.ts`) is false, the Worker leaves `authentication` out of its answer and the app says nothing about authentication; the field is kept in `auth_results` from the first day (`test/unit/original.test.ts` holds the switch to the ledger entry). **On a development instance nothing checks authentication**: the local runtime builds the message's headers from what was posted, so an `Authentication-Results` field the sender wrote with the platform's identifier is believed and stored there. An arrival that is finished later has no such field: it went with the handler that was stopped. The cut of decision 19 takes the platform's own field to be well formed: if the platform ever wrote a quoted string or a comment that it did not close, a field of the sender's that follows could close it, and what is kept would then run into the sender's field. Podbay cannot tell that case from the value; the live check is where it would show. A left-over arrival in a mailbox that gets no more mail stays as it is until mail arrives (no timer is decided), and two messages arriving at once can both take it up, in which case it may be filed as `interrupted` though it could have been read; the message and its original are kept either way. A file whose bytes could not be written after its row stays a row that is not shown, and nothing writes it again from the original. The platform does not document what the sending server is told when the handler throws (it throws only before the original is stored). The whole file passes through the browser's memory before it is saved. The local development endpoint refuses a message its own parser refuses, so the screen for a message that could not be read is tried in the browser with a text that is too large, and the other two reasons in the Workers runtime only. Deleting a mailbox does not stop mail that is arriving in the same moment: a message whose handler was past the recipient check when the mailbox went can still write into the emptied mailbox object.
- **A person's choices and known addresses ([ADR-0012](adr/0012-a-persons-choices-and-known-addresses.md)): what is left.** A recipient has no name: the sending bodies carry bare addresses, so `name` stays empty until a later decision lets them carry one (decision 16); the completion already matches a name and shows it beside the address. An open tab learns of a choice made elsewhere when it is loaded or come back to, not at once ([ADR-0013](adr/0013-the-mailbox-tells-the-open-app.md)). A member can still walk the alphabet through the completion, a few answers at a time: the route is not rate-limited, like every route but sign-in. Replying to all teaches every recipient, also one a stranger put in Cc. The mailbox learns from whatever leaves through the one function that lets mail leave (ADR-0016): when mail the Worker sends by itself is built ([ADR-0008](adr/0008-rules-for-incoming-mail.md)), it leaves through the same function with the kind `auto` and must not be learned from there. Known addresses are not in an export, mail already in Sent is not read back, and there is no switch that stops a mailbox from remembering. The order of a list travels as an eleventh choice, by decision 25 of ADR-0014; ADR-0012 names ten. No route deletes an account, so that the row of choices goes with it is proven by deleting the row of the person in the database. Nothing was tried with two real devices: the second browser of the tests is a second context of the same Chrome.
- **The mailbox tells the open app ([ADR-0013](adr/0013-the-mailbox-tells-the-open-app.md)): what is left.** The record names four things the platform's documents do not settle. (1) *Whether tags outlast the object's sleep:* yes in the local runtime, where the test evicts the object with its connections open and finds each connection by its person's tag afterwards; not shown on Cloudflare's network. (2) *Whether a `ping` the platform answers is billed as a received message:* not settled and not testable here, since nothing local counts billing; the pricing page says only that such an answer is not charged wall-clock time. At twenty to one it would be three requests an hour for an open tab. (3) *Whether a silent WebSocket is closed after a while:* locally a connection on which nothing was said for 130 seconds stayed open and was still told (the suite runs it with 65); no page says what Cloudflare's network does, and the app does not depend on it, since it pings every minute and reconnects. (4) *Whether `'self'` covers the WebSocket address:* yes in the installed Chrome for `ws:` on the `http:` page the tests serve, with no report; `wss:` on an `https:` page, and every other browser, is not tried, because the test instance has no certificate. A browser that refuses is told to stop by its own policy report and goes on asking; that path has no test. All four are in the ledger, the unsettled ones as `needs verification`. **Also open:** a session that ends is not known to the object, so a connection opened before is told for up to five minutes more (decision 13); "held" for the waits is ten seconds open, and a connection closed to make room for a ninth tab waits the longest wait before coming back, both chosen here; a write that sets a value a row already has counts as a change, so it can cost a refetch that finds nothing new; the first message of a tab's first connection makes it read its lists once more; a tab does not know its own change from another's (the record leaves that open); nothing counts connections or refusals for an operator to see; the assistant's own connection is as it was: it is not closed when a membership ends and has no five minutes.
- **Outgoing mail ([ADR-0016](adr/0016-outgoing-mail-waits-before-it-leaves.md)): what is left.** **What cannot be known:** if the sending service took a message and its answer was lost, Podbay cannot find out: `send()` takes no key to ask with. Such a message is in Drafts again, marked not sent, and says that it may have been sent; a person decides, and sending it again may send it twice. There is no "mark as sent". An `unknown` keeps its place in the caps. **The stored id of a sent message** is still the one Podbay made and never gave to the service; the service's id is kept beside it and nothing uses it: no delivery, bounce or complaint event is read, and an `unknown` is not settled from them. **Decided while building, for the lead to see:** an argument of the wrong shape (a `TypeError` without a code) and a file whose bytes are gone at leaving are recorded as `limits`, since the record's list of reasons is closed; at the press an ordinary send counts the messages that wait to leave before it against the caps, so that a burst inside one window cannot pass twenty; a message sent as text alone is stored as HTML made from that text, so that one body holds everything the service is given, and leaves with both forms; marking a waiting message read or starred is refused like the changes the record names; `late` is asked before `right`; a request that names a waiting message for a deed on many conversations is refused whole, while a deed on a conversation or a search passes over it; `createEmail` no longer stores into Sent or Scheduled at all. **Not built:** a notice when a send fails for a person whose app is closed (the record leaves it open: the rail and the line say it at the next look); a cap for the whole instance; editing a waiting message in place; showing who scheduled a message. A failed message a person did not send themselves is said by the rail's mark and the line, with no note. A waiting message that a search across places finds is a line like any other there: a deed on it from that list is refused by the mailbox, and the app says that not everything could be changed. The mark of a failed message stays on its row when the draft is moved to Trash and is not counted there. **The app:** after the window it asks the mailbox once a second, for twenty seconds, whether the message left, and then says that it still waits; the note with Undo can be closed, which takes Undo away for that message but not the window; "Send and archive" files the conversation at the press and says so when the message has left. **Not tried on Cloudflare's network:** that `ctx.id.name` is there in an alarm, that an alarm is at most a minute late, and the service's refusals: all of it is tried in the local runtime with a send binding of the tests, and the local binding of development never refuses. The retry times were tried by ageing rows, not by waiting. **In the tests** an alarm whose time has come runs by itself, so a test that must see one run sets a time that has not come and runs it by hand.
- **Rules for incoming mail ([ADR-0008](adr/0008-rules-for-incoming-mail.md)): what is left, and what was chosen while building.** *Not decided by the record and not built:* applying a filter to mail that is already here, forwarding and rejecting, an allow list, importing and exporting rules. *Blocking goes by the address a message says it is from.* That is the sender's text: someone who is blocked and writes under another address is not blocked. The envelope sender is used for filing only for a message that could not be read; the automatic reply, which goes to the envelope sender, asks the block list about that address too. A blocked domain is that domain, not what is under it. *"Contains the words"* reads the subject and the first 20,000 characters of the text; each word must be there, in any order. *A label a rule gives* is skipped when it was deleted since; the rule keeps its id. *Two owners saving the filters at once lose one change:* the route replaces the whole list. *The automatic reply:* it is sent from the mailbox's address without the name mail is sent under, and its subject, when none was given, is the English "Automatic reply". It names no message it answers (`In-Reply-To` is left out, a strict reading of "none of the incoming message"), so the other side's mail program does not put it under the question. Mail a rule moved to Trash is not answered either, which the record does not say. Each reply is kept in Sent as a message of its own. A reply the service refuses, or does not answer for, is removed and that sender is not tried again for seven days. While a reply waits (a full cap, or "not now" from the service) it is in Scheduled like any message; nobody can take it back or give it a time: both routes answer 404 for it. The right asked again when a reply leaves is `mailbox.manage` of the person who saved it. *Once in seven days is per exact address:* `name+1@` and `name+2@` are two senders and each is answered, within the reply's own caps; folding them was not chosen, because what a `+` means belongs to the other side's domain. *The record of answered addresses* is pruned of what is older than seven days on every save and when a reply is made, emptied when the reply is turned off, and loses the entry of a reply that did not leave for a reason of the mailbox (off, past its end, the saver's right, late, the sender check, the limits); a reply the service refused keeps its entry. A reply turned on again is a new absence, so its senders are answered again. Its own caps (10 in an hour, 50 in a day) were chosen here. Replies are not in the audit log; saving the reply is. `Auto-Submitted` is on the sending service's list of headers by its documentation; no reply was seen on Cloudflare's network. *A mailbox made before 2026-11-18* may still hold `forwarding` and `autoReply` in its settings; nothing reads them, and the settings route still asks fresh proof for a change of `forwarding`. *Coverage is by tests, not measured:* no coverage tool is installed, so "full branch coverage" of the pure function is a test for each branch, read by hand. *The guards taken out once, each failing its test:* the reply being off, filed away, `Auto-Submitted`, a list, not addressed, a sender that is not an address, the mailbox itself, a program's address, seven days, the hour, the day, the mailbox's caps, the header, the envelope sender, the kind `auto`, not learning, removing a failure, fresh proof, the guard around the reply, a subject taken from the message, the right at leaving; and for rules: blocked first, the guard around the rules, no label in Spam, own labels only, the two rights, the order of places, the limit of blocked senders, the audit detail, the strict vocabulary. "Only a message that was read is answered" is held twice (the check itself, and that such a message names no recipient): taking out one fails nothing, taking out both fails its test. Taken out on 2026-11-18 after the audit of the draft, each failing its test: the envelope sender asked of the block list, the assistant woken for the Inbox only, the reply asked again at leaving, its record taken back, the two routes refusing a waiting reply, the text and HTML in agreement, the kind of a block, `mailbox.manage` at leaving, the record emptied when turned off. Taken out on 2026-11-18 after the second audit, each failing its test: the mailbox under a `+tag`, the mark that stops a reply, the save a waiting reply was made from, the limited reader at the rules routes, the screen saving only what it shows, the input lowered once in the HTML scanner. That an arrival finished by the next one is answered once is a regression test with no single guard to take out: the arrival's row is removed in the transaction that files it. *Not decided by the record, and how it is now:* who is never answered is RFC 3834's list and nothing more, so a no-reply or postmaster local part, and `Precedence: auto_reply`, are answered; the authentication results of a message are not asked before a reply is made; a parsed message with no `From`, or a group as its `From`, has no sender for the block list and lands in the Inbox; filters and blocks need no fresh proof (decision 7), and their audit rows hold counts only. *Not yet seen on a real account:* the ledger records that the sending service takes `Auto-Submitted` in its `headers` map, but whether the field is carried on the wire, and which envelope sender the service puts on a reply, were never seen: every reply so far went to a send binding of the tests. Not tested in a browser: that "Block the sender" is not offered for a sender without an `@`.
- **Emptying goes by the date of a message.** "What was there when it was asked" is decided by the date a message carries, which for incoming mail is the time it arrived. A message with an older date that is moved into Trash while Trash is being emptied goes with the rest.
